### 3. 受入条件（AC）

> 節の区分: 生成物。書き方は 03 §2.1 に従う。
> ルール: 表の 1 行 = 1 AC = 1 つの検証可能な振る舞い／観測可能な結果のみ／曖昧語禁止。期待値の詳細は AC に写さず、根拠の `C-xx`（5.2 の行）で指す。流れの AC も表に 1 行置く。
> テストレベルは `受入` / `結合` / `単体`（01 §2）。検証層は `層1` / `層2（Integration）` / `層2（E2E）`。複数の層で検証するときは、読点で並べる。E2E は、検証層の列に許可領域を書く（例: `層2（E2E: happy-path）`。02c §5.1）。
> 根拠の列は空にしない。`C-xx`、要件 ID、設計 ID（`DES-…`）、OI のどれかを書く。
> Gherkin にするのは、流れの AC と、期待値が未決（`@pending:<OI-ID>`）の AC だけである。今は未解決の Blocking が無いので、`@pending` の AC は無い。
> テスト名は、先頭に `AC-xx-yy` を置く。括弧やコロンで囲まない（03 §3.4）。テストとの対応は、TRS ファイルの 7 に書く。
> `AC-xx-yy` の `xx`（UC の番号）は、他の TRS と重複させない（03 §3.4.2 の ④）。

応答の形と値の約束は、次のとおりである。

- 入力の拒否は 400、存在しない対象は 404、成功は 2xx である（OI-001、OI-006）。
- 拒否の本文は ProblemDetail（RFC 9457）に、理由コードの配列 `codes` を足した形である。本文の `status` は HTTP ステータスと同じ値である（OI-018）。
- `codes` は、要素の集合で比べる。順序は仕様にしない（DES-TODO-30）。
- 区分は「未完了」「完了」「期限切れ」のラベルで表示する（OI-010）。
- 現在時刻を固定するのは、層1と Integration だけである。E2E は実時間で動くので、期限は「今日より前」のように相対で書く。

#### 補足

- 登録の古い順の例は、時計を進めて、登録時刻が異なるように登録した例に限る。登録時刻が完全に同じ場合の順は、AC-05-07 と AC-05-08 で決める。
- タイトルは Unicode 正規化をしない（OI-008）。読み戻したタイトルは、前後の空白と表示されない文字を除いた以外は、入力と同じコードポイント列である（OI-017）。

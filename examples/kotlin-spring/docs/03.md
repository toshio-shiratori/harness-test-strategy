# 03 TRS ガイドラインのサンプルでの実現（Kotlin + Spring Boot）

[03 TRS 策定ガイドライン](../../../docs/testing/03-trs-guideline.md)は言語中立の規範です。この文書は、そのうち Kotlin のサンプル（`examples/kotlin-spring/`）で規範をどう実現しているかを記録します。規範そのものは 03 を正とします。ここに書いた選択は、このサンプルの例であり、導入先に求めるものではありません。

## 1. TRS の配置（03 §1）

規範は「導入先の TRS ディレクトリに `<機能ID>-<機能名>.md` として置く」です。このサンプルでは次のとおりです。

| 対象 | 置き場所 |
|---|---|
| サンプルの要件定義書（TODO-001） | `examples/kotlin-spring/docs/requirements/` |
| サンプルの基本設計書（TODO-001） | `examples/kotlin-spring/docs/basic-design/` |
| サンプルの TRS ファイル（TODO-001。人が合意する節と運用情報） | `examples/kotlin-spring/docs/trs/` |
| サンプルの TRS の生成物（US、UC、AC、組合せ別の期待結果） | `examples/kotlin-spring/docs/trs/generated/`。TRS ファイルと同じ名前で置く |
| 要件定義書のテンプレート | [`docs/testing/templates/requirements.md`](../../../docs/testing/templates/requirements.md)（標準の側） |
| 基本設計書のテンプレート | [`docs/testing/templates/basic-design.md`](../../../docs/testing/templates/basic-design.md)（標準の側）。`TraceabilityTest` は読みません |
| TRS のテンプレート | [`docs/testing/trs/_template.md`](../../../docs/testing/trs/_template.md)（標準の側） |

規範は、生成物のサブフォルダの名前を導入先が決めると定めています（03 §5.4）。このサンプルは `generated` にしました。`TraceabilityTest` は、`docs/trs/` の TRS ファイルと、`docs/trs/generated/` の生成物のファイルを、同じ名前で組にして読みます。`docs/requirements/` の全要件定義書と、`docs/basic-design/` の全基本設計書も読みます。基本設計書で設計 ID として読むのは、節 2〜9 の表の先頭列だけです。設計 ID は、根拠の実在と網羅の照合に使います。要件定義書と基本設計書は、目次と用語の検査にも使います。テンプレートは、次の 3 つを読みます。

- `../../docs/testing/trs/_template.md`
- `../../docs/testing/templates/requirements.md`
- `../../docs/testing/templates/basic-design.md`

目次の自己テストは、規範（`../../docs/testing/03-trs-guideline.md` の 5.2）も読みます。パスは、`examples/kotlin-spring/` で実行するときの相対パスです。

`build.gradle.kts` は、次を `./gradlew test` の入力にしています。

- `docs/trs`、`docs/trs/generated`、`docs/requirements`、`docs/basic-design`
- 上のテンプレートと規範

入力に宣言しないと、変更しても `test` が再実行されず、検査が素通りします。

## 2. データ駆動テストへの展開（03 §2.3）

規範は「データ駆動テストに使う機能は、導入先が1つに決めて標準とする」です。このサンプルは Kotest の `withData` を標準にし、JUnit5 の `@ParameterizedTest` は採用していません。理由は次のとおりです。

- このリポジトリのテストは Kotest に統一されている。
- `@ParameterizedTest` には `junit-jupiter-params` の追加が必要で、実際に動かして検証できない例を書くことになる。

```kotlin
class TaskCategoryTest : FunSpec({
    // AC-04-01 が根拠にする制約表 5.2 の行（C-10〜C-13）を、1 行 1 ケースにする。id は制約 ID で、期待結果は制約表の値
    data class Case(val id: String, val state: TaskStatus, val due: String?, val now: String, val expected: TaskCategory)

    context("AC-04-01 タスクの区分は、完了・期限・現在時刻で決まる（C-10〜C-13）") {
        withData(
            nameFn = { "${it.id} ${it.state} 期限 ${it.due} 現在 ${it.now} → ${it.expected}" },
            ts = listOf(
                Case("C-10", TaskStatus.Open, null, "2026-11-01T10:00+09:00", TaskCategory.Open),
                Case("C-11", TaskStatus.Open, "2026-11-02", "2026-11-01T10:00+09:00", TaskCategory.Open),
                Case("C-11", TaskStatus.Open, "2026-11-01", "2026-11-01T00:00+09:00", TaskCategory.Open),
                Case("C-11", TaskStatus.Open, "2026-11-01", "2026-11-01T23:59:59.999+09:00", TaskCategory.Open),
                Case("C-12", TaskStatus.Open, "2026-11-01", "2026-11-02T00:00+09:00", TaskCategory.Overdue),
                Case("C-12", TaskStatus.Open, "2026-11-01", "2026-11-05T12:00+09:00", TaskCategory.Overdue),
                Case("C-13", TaskStatus.Done, null, "2026-11-01T10:00+09:00", TaskCategory.Done),
                Case("C-13", TaskStatus.Done, "2026-11-01", "2026-11-01T10:00+09:00", TaskCategory.Done),
                Case("C-13", TaskStatus.Done, "2026-11-01", "2026-11-02T00:00+09:00", TaskCategory.Done),
                Case("C-13", TaskStatus.Done, "2026-11-01", "2026-11-05T12:00+09:00", TaskCategory.Done),
            ),
        ) { it ->
            task(it.state, it.due).category(clockAt(it.now)) shouldBe it.expected
        }
    }
})
```

上の例は、TODO-001 の AC-04-01（`TaskCategoryTest.kt`）です。制約表（§5.2）の制約 ID（C-10〜C-13）の各行を 1 ケース以上にし、制約 ID をケース名の先頭に置きます。入力の値は、因子・水準の表（F3、F2、F4）の水準から取ります。期待結果は制約表の値で、実装の挙動から逆生成していません。制約表と AC は、要件定義書と基本設計書から生成したものです（03 §3.1）。`task`・`clockAt` などのテスト内の定義と、同じファイルの境界・PBT のテストは省いています。他の制約の行は、`TaskConstraintTableTest.kt` で同じ形に展開しています。1 行を 1 ケースにし、禁止の組合せ（§5.1）はケースにしていません。Kotest 6.2.5 での実測で分かった点は次のとおりです。

- `withData` は `io.kotest.datatest.withData`。`kotest-runner-junit5` が持ち込む `kotest-framework-engine` に含まれ、追加の依存は要らない。
- `StringSpec` の `"名前" { }` の中に `withData` を置くと、「Nested withData is not supported inside StringSpec test bodies」で非推奨になる（`allWarningsAsErrors` によりビルドエラー）。AC 名のコンテナの下に置くには `FunSpec` の `context(...)` などを使う。
- 位置引数だけで呼ぶと `withData` のオーバーロードが曖昧になるため、`nameFn` / `ts` を名前付きで渡す。
- コンテナ名の先頭の AC ID は `TraceabilityTest` が文字列リテラルとして拾うので、検査側の変更は不要。

[TODO-001](./trs/TODO-001-task-management.md) の §4 は、組合せ生成方針に、組合せを展開しない理由を書いた例です（テンプレート §4 の注記）。因子が独立な登録の検証（タイトル × 期限）が、その例です。一方、区分の判定（完了 × 期限 × 現在時刻）は、制約表（§5.2）に全組合せを書いています。

## 3. トレーサビリティ検査の実装（03 §3.4）

規範の「トレーサビリティ検査」は、このサンプルでは `TraceabilityTest`（Konsist）と、その検査の部品が実装しています。部品は、`src/test` の `architecture` パッケージにある次のクラスです。

- `TrsSetCheck`、`UnresolvedBlockingCheck`、`RequirementTraceCheck`
- `DesignIds`、`InputDocCheck`

検査は、`./gradlew test` で実行します。

### 3.1 テスト名の付け方

- Kotest の文字列名・JUnit のバッククォート名のどちらでもよく、grep で機械的に辿れる。
- JVM のバッククォート名は `[` `]` `:` `.` を使えないため、`AC-xx-yy` を括弧やコロンで囲まない（旧サンプルの検証で判明）。
- TRS ファイルのトレーサビリティ表の項目は、`<テストクラス名>::<AC ID>` の形である。表は手で書かず、テストコードから作る（[3.5](#35-トレーサビリティ表のテスト名の生成)）。

### 3.2 検査の対象

| 検査 | サンプルでの実現 |
|---|---|
| 検査の単位 | `TrsSetCheck` が、`docs/trs/` の TRS ファイルと、`docs/trs/generated/` の同じ名前の生成物のファイルを組にして読み、03 §3.4 の失敗条件を検査する。条件は 03 §3.4 を参照する |
| 規範より厳しい点 | 次の 11 点は、規範の失敗条件にない。このサンプルが選んだ検査で、導入先には求めない。(1) 生成物のファイルにあるトレーサビリティ表、(2) AC の表の 7 列の見出しの完全一致、(3) 同じ TRS の中の AC 行の重複、(4) 5.2 の表が無いファイル、(5) `制約ID` を含む、見出しの違う表、(6) AC の根拠の `C-xx`・要件 ID・OI の実在と、空欄・形の判定（設計 ID は ⑨ が規範にある）、(7) トレーサビリティ表の一致（[3.5](#35-トレーサビリティ表のテスト名の生成)）、(8) 設計 ID が 1 件も読めないことを、基本設計書ごとに調べること、(9) 用語の表の列数と、言い換えの空の語、(10) 基本設計書の表の見出し行にある設計 ID の形を、失敗にすること、(11) 言い換えの語が用語の列の語と同じ用語の表を、矛盾として失敗にすること |
| AC の表の読み取り | 見出しが 7 列（`AC ID` / `関連 UC` / `テストレベル` / `検証層` / `優先度` / `検証する振る舞い` / `根拠`）に完全に一致する表だけを、AC の表として読む。トレーサビリティ表の行は読まない |
| AC に対応するテストの検査（①） | `TestNameCheck` が、AC の表から `AC-xx-yy` を取り、`src/test`・`src/integrationTest`・`src/e2eTest` にその ID で始まるテスト名があるかを照合する。無ければ失敗させる。`@pending` の AC は外す |
| テスト名の `AC-xx-yy` の実在（⑦） | 同じ `TestNameCheck` が、テスト名の先頭の `AC-xx-yy`（空白区切りで並ぶものはすべて）を集め、どの TRS の AC の表にも無ければ失敗にする。自己テストの文字列は、テスト名ではないので `selfTestFiles` として除く |
| 未解決の Blocking な Open Issue の検査 | `UnresolvedBlockingCheck` が、TRS ファイルの Open Issues 表を読み、03 §3.4.2 の ② ③ と §3.4.3 の書式を検査する。`@pending` は、生成物のファイルの Gherkin から読む |
| 照合から外す記録 | 未解決でない行（`Resolved`、`Superseded`、`Won't Fix`）の反映先に `AC-xx-yy 削除` と書いた AC は、関連列とトレーサビリティ表の照合から外す。カンマで区切って並べ、範囲表記と未解決の行は読まない（`TrsSetCheck.exemptions`）。未解決の Blocking の関連列の AC が、すべて削除の記録で外れるときは失敗にする。一部なら、残りの AC を調べる |
| トレーサビリティ表の照合 | TRS ファイルのトレーサビリティ表（見出しが完全一致する表）の AC ID を、AC の表と照合する。範囲表記は展開し、読めない表記は失敗にする。行の区分と状態は問わない |
| トレーサビリティ表の一致 | `TraceabilityMatrixTest` が検査する。詳細は [3.5](#35-トレーサビリティ表のテスト名の生成) |
| 組合せ別の期待結果の書式 | `ExpectationTable` が、見出しが完全一致する 5.2 の表を読み、03 §3.4.3 の判定の表を検査する。語は部分一致で、例外は `未決済`・`未定義` である |
| 根拠の実在 | `BasisCheck` が、AC の表の根拠を半角のカンマで分け、実在を照合する。`C-xx` は同じ組の 5.2、要件 ID は要件定義書、設計 ID は基本設計書の節 2〜9 の表の先頭列（`DesignIds`）、OI は TRS ファイルの Open Issues 表である。5.2 の根拠は、設計 ID だけを同じ判定で調べる（⑨）。`DES-` で始まるのに書式が違う値は、別の文言で失敗にする。意味の一致は検査できないので、AI のレビューが補う |
| テンプレートの検査 | `docs/testing/trs/_template.md` を同じ `UnresolvedBlockingCheck` と、`TrsSetCheck.contentViolations`（AC の表・5.2・トレーサビリティ表）に通す。テンプレートは全節を 1 ファイルで示すので、組の検査と根拠の実在は通さない。テンプレートの未解決の Blocking（OI-001・OI-003）の AC には `@pending` が付いており、Open Issues 表は読める書式になっている |
| `AC-xx-yy` の重複（④） | 全 TRS の生成物のファイルの AC の表を集め、別の TRS が同じ ID を持てば失敗させる。トレーサビリティ表の ID は数えない。照合はテスト全体のテスト名に対して行う |
| 要件 ID の網羅（⑤） | `RequirementTraceCheck` が、全要件定義書の要件 ID が、全生成物のファイルの US/UC の出典に現れるかを照合する。現れない ID は失敗にする |
| 出典の実在（⑥） | 出典の値が要件定義書にある要件 ID かを照合する。同じ要件 ID が複数の行にあるときも失敗にする |
| 設計 ID の網羅（⑧） | `TrsSetCheck` が、全基本設計書の設計 ID（`DesignIds`）が、全生成物のファイルの、AC の表と 5.2 の根拠に現れるかを照合する。`@pending` の AC の根拠も数える。現れない ID は失敗にする |
| 設計 ID の実在と重複（⑨） | 根拠の設計 ID が、基本設計書の節 2〜9 にあるかを照合する（AC の表と 5.2）。同じ設計 ID が全基本設計書で複数の行にあるときと、書式の違反（[3.3](#33-要件設計との対応の検査と入力の文書の検査の読み取り03-343345)）も失敗にする |
| 目次（⑩） | `InputDocCheck` が、要件定義書と基本設計書の、番号つきの `##` 見出しを、03 §5.2 の目次と照合する。番号・名前・順序・数のどれかが違えば失敗にする |
| 用語の言い換え（⑪） | `InputDocCheck` が、要件定義書の用語の表の「使わない言い換え」を集め、同じ名前の要件定義書・基本設計書・TRS ファイル・生成物のファイルの本文を調べる。検査しない節は [3.3](#33-要件設計との対応の検査と入力の文書の検査の読み取り03-343345) に書いた |
| 書式の検査 | 要件定義書・基本設計書・生成物のファイルの書式が読めないときも失敗にする。読み取りの細目は [3.3](#33-要件設計との対応の検査と入力の文書の検査の読み取り03-343345) に書いた |
| ⑤ ⑥ のテンプレートの検査 | テンプレートの TRS と要件定義書（`REQ-CNL-01`〜`04`）の組を、同じ検査に通す |
| ⑩ のテンプレートの検査 | テンプレートの要件定義書と基本設計書を、⑩ に通す。用語のテンプレートの表が、⑪ の読み取りで読めることも確かめる。目次の定数が 03 §5.2 と同じことも確かめる |

### 3.3 要件・設計との対応の検査と入力の文書の検査の読み取り（03 §3.4.3〜§3.4.5）

失敗にする条件は、03 §3.4.3（書式）、§3.4.4（⑤ ⑥ ⑧ ⑨）、§3.4.5（⑩ ⑪）を正とします。ここには、`RequirementTraceCheck`・`DesignIds`・`InputDocCheck` が規範の細目を決めた点だけを書きます。次の表は、要件定義書と生成物のファイルの読み取り（⑤ ⑥）です。

| 項目 | サンプルの実現 |
|---|---|
| 読む範囲 | `docs/requirements/` の直下の `*.md` と、US/UC は `docs/trs/generated/` の `*.md`。要件定義書と生成物のファイルは、`_` で始まる名前も読む。`_` で始まるものを除くのは、TRS ファイルだけである（旧版どおり。`_template.md` などの置き場の都合） |
| コードブロック | 開いた文字（`` ` `` か `~`）と同じ文字を、開いた長さ以上に並べた行で閉じる。中は見出しにも表にも読まない |
| HTML コメント | 中は見出しにも表にも読まない。想定外の書き方で、中の要件 ID は表の外の文字列として失敗にする |
| 表の見出し行・区切り行 | 表の 1 行目を見出し行、2 行目を区切り行とみなす。要件の表は、2 行目が区切り行でないとき失敗にする |
| 要件の節の終わり | 次の同じ深さ以上の見出し。節の中の小見出しの表も読む |
| 要件 ID の定義 | 先頭列だけ。備考列など、ほかの列の要件 ID は定義に数えない。見出し行の要件 ID の形も失敗にする |
| US の表 | 見出し行に `出典（要件 ID）` の列がある表、または先頭列が `US-<数字>` の行を含む表。見出し・区切り以外の行は、先頭列が `US-<数字>` で、列数が見出しと同じでなければ失敗にする |
| UC の節 | 見出しが `UC-<数字>:` で始まる節。コロンは全角の `：` も可。節は、次の同じ深さ以上の見出しまで |
| UC の見出しの形 | `UC-<数字>` で始まるのに `UC-<数字>:` の形でない見出しは失敗にする |
| UC の出典の行 | 項目名が `出典（要件 ID）` の行は、列数を 2 とする。UC の節に属さない行は失敗にする |
| 出典の区切り | 半角のカンマだけ。全角の読点は区切りと読まず、要件 ID の形でない値として失敗にする |
| 生成物のファイルの表の外 | 要件 ID を検査しない。AC の表の根拠の要件 ID は、`BasisCheck` が別に検査する |
| 失敗メッセージ | 先頭にファイル名を付け、違反を全件出す |

設計 ID の読み取り（⑧ ⑨）は、`DesignIds` が次のとおり決めています。

| 項目 | サンプルの実現 |
|---|---|
| 読む範囲 | `docs/basic-design/` の直下の `*.md`。`_` で始まる名前も読む |
| 節の見分け方 | `##` 見出しの先頭の番号。`## 2.` から `## 9.` の節の表だけを、設計 ID の定義として読む。コードブロックと HTML コメントの中は表にしない |
| 設計 ID の定義 | 先頭列だけ。ほかの列にある設計 ID の形の文字列は、定義に数えず、失敗にもしない（ほかの項目を指す参照として書ける） |
| 書式の失敗 | 先頭列が設計 ID の形でない行、見出し行の設計 ID の形、節 2〜9 の表の外の設計 ID の形、設計 ID が 1 件も読めない基本設計書、同じ設計 ID の重複 |
| 0 件の判定 | 基本設計書ごとに調べる。規範は「基本設計書があるのに 0 件」と書くだけで、複数の基本設計書の範囲を決めていない |
| `DES-` で始まる書式違反 | 根拠の列だけを調べる（`BasisCheck`）。基本設計書の本文には、`DES-<略号>-<番号>` のような書式の説明があってよい |
| 網羅の照合先 | 全生成物のファイルの、AC の表と 5.2 の根拠。書式の違う値は、現れたと数えない |

入力の文書の検査（⑩ ⑪）は、`InputDocCheck` が次のとおり決めています。

| 項目 | サンプルの実現 |
|---|---|
| 目次の正 | 03 §5.2 の 2 つの一覧を、`InputDocCheck` の定数に写した。定数が規範と同じことは、`TraceabilityTest` が 03 の 5.2 を読んで確かめる。テンプレートも ⑩ に通す |

### 3.4 AC の番号の割り当て（03 §3.4）

規範は「`xx` は TRS ごとに異なる番号を割り当て、新しい TRS は既存の TRS が使っていない最小の番号から採番する」です。このサンプルでは次のとおりです。

| TRS | `xx` |
|---|---|
| TODO-001 | `01`〜`06`（UC-01〜UC-06 の番号） |

03 §3.4.2 の ④ により、`xx` は UC の番号を使います。`xx` は TRS ごとに異なる番号を割り当てるので、UC の番号も TRS 間で一意になります。TODO は TRS が 1 本なので、TRS 間の重複の検査（④）は、2 本目の TRS を足したときに働きます。2 本目は `07` から採番します。TRS を 1 本にした理由は、[5.4](#54-trs-を-1-本にした理由) に書きました。

### 3.5 トレーサビリティ表のテスト名の生成

規範は、トレーサビリティ表（テンプレート §7）を運用情報とし、生成の方式を定めていません。サンプルの TRS ファイルの表は、テスト名を手で書いていました。これを、テストコードから作る形に改めました。表の作り方は、`TraceabilityMatrix`（`src/test` の `architecture` パッケージ）にあります。検査の保護の対象です。

方式は、次の 2 つから選びました。

| 方式 | 内容 | 選んだか |
|---|---|---|
| 検査型 | 層1のテストが、テストコードと AC の表から表を作る。TRS ファイルの表と一致しなければ失敗にし、置き換える表の全文をメッセージに出す | 選んだ |
| 書き換え型 | 生成コマンドが、TRS ファイルの表を書き換える | 選ばなかった |

検査型を選んだ理由は、手で直した値が残らないことです。書き換え型は、コマンドを実行し忘れると、古い表が残ります。それを止めるには、一致を調べる検査が要ります。検査型は、その検査だけで足ります。表の更新は、失敗メッセージの表で置き換えるだけです。

表の各列は、次のように決まります。

| 列 | 導き方 |
|---|---|
| 行 | 生成物のファイルの AC の表と同じ集合、同じ並び |
| 層1 | `src/test` のテストファイルのうち、テスト名の先頭にその AC ID を持つもの。項目は `<クラス名>::<AC ID>`。クラス名はファイル名と同じで、辞書順に並べる |
| 層2 | `src/integrationTest` と `src/e2eTest` の同じもの |
| 層3 | AC の表の検証層に `E2E` を含む AC は `探索対象`、含まない AC は `—`。探索は画面を操作するので、画面で検証する AC を対象にする |
| 状態 | 生成物のファイルで、① と同じ正規表現で `@pending:<OI-ID>` を読んだ AC は `pending（<OI-ID>）`。読まず、テストがあれば `実装済`、無ければ `未着手` |

規範との違いと、既存の検査との違いは、次のとおりです。

- 項目の形: 03 §3.4.1 は、テストの所在とテスト名を `::` でつなぐ形を定めます。このサンプルは、テスト名を、名前の全文ではなく AC ID にしました。名前の全文は長く、説明を直すたびに表が変わるためです。所在はクラス名です。
- 完全一致: この検査は、表が AC の表と完全に一致することを求めます。
- 照合から外す記録: `AC-xx-yy 削除` の記録は、この検査には効きません。AC の表に無い行は、記録があっても失敗にします。
- 範囲表記: 表の範囲表記の行も、失敗にします。AC を消したときは、表からも行を消します。

テスト名の読み方は、AC に対応するテストの検査（①）と同じ関数を使います。

- 層3 の規則は、今の `探索対象` の付いた AC と、検証層に E2E を含む AC が、同じ集合だったので導けました。規則を変えるときは、`TraceabilityMatrix` を直します。
- 生成に切り替えて変わった行は、2 つです。AC-01-33 と AC-01-36 の層1の項目の並びが、辞書順になりました。
- 自己テストは `TraceabilityMatrixTest` にあります。実ファイルが一致することと、一致すれば合格することを確かめます。書き換えた値、増えたテスト、足りない行、余った行、重複、列数、並び、表が 0 個または 2 個のときは、失敗にします。
- 自己テストの AC ID は、`ac(n)` で組み立てます。ソースに `"AC-xx-yy` の形の文字列を書くと、① ⑦ が、テスト名と取り違えるためです。`selfTestFiles` に足すと、検査から外す変更になるので、足していません。
- `src/integrationTest` と `src/e2eTest` のテスト名も読みます。`build.gradle.kts` が、この 2 つを `test` の入力に宣言しています。

ただし、合意の向きは規範と違います。サンプルの TRS は、2026-11-01 に AC に個別に合意しました。規範は、AC を生成物とし、個別に合意しません。今の AC は、合意した AC を規範の形に書き直したもので、今の入力から生成し直したものではありません。

規範には、新しい検査が 4 つあります（03 §3.4）。

このサンプルでの実現は、[3.2](#32-検査の対象) のとおりです。生成物の別ファイル化は、同じ PR で行いました（#294）。

PR の CI は、base との差分から、既存の ID の変化を列挙します。PR 本文に ID ごとの理由が無ければ、失敗にします。詳細は [5.8](#58-既存の-id-の変化を列挙する-ci03-51) です。

### 5.2 規範の順とのずれ

### 5.4 TRS を 1 本にした理由

03 §1 は、1 機能（1 ユースケース群）を 1 ファイルにし、仕様の経緯を複数のファイルに分散させないと定めています。TODO の要件定義書は、機能名が 1 つで、対応する TRS を 1 つとして書いています。登録、完了、一覧、表示の切り替えは、同じタスクの状態を共有します。期限切れの区分の因子制約が、登録と一覧にまたがります。そのため、TRS は 1 本にしました。生成物は別ファイルに置くので、1 本の TRS は、TRS ファイルと生成物のファイルの 1 組です（[5.7](#57-規範の形への移行294)）。

### 5.8 既存の ID の変化を列挙する CI（03 §5.1）

規範は、既存の ID に結び付く記述の変化を、人がレビューする対象とします。導入先は、変化を機械で列挙して人に示すとよいとされています。サンプルは、PR の CI で列挙し、PR 本文の理由の欄に、人が見たことを残します。実装は、`scripts/check-id-changes.mjs` と、ワークフロー `pr-id-changes-check.yml` です。

列挙する対象は、生成物のファイルの、base と head の差分です。比べる起点は、base と head の merge-base です。base の先端と比べると、分岐の後に base へ入った変更が、この PR の変化になるためです。

| 種類 | 列挙する条件 |
|---|---|
| 消えた | US の行、UC の節、AC の表の行、`C-xx` の行が消えた |
| 中身が変わった | 上の記述の中身が変わった。シナリオの Examples の行の変化を含む。AC の表の行を残して、シナリオだけが消えた、または足された変化も含む。空白の違いと行の並べ替えは、変化にしない |
| `@pending` になった | 既存の AC に `@pending` が付いた。新しい AC が最初から `@pending` のときは、列挙しない |
| 使い回し | 過去に使った ID が、新しい行として戻った |
| `Gherkin共通` | ID に結び付かない Gherkin（`Feature`、`Background`、タグのないシナリオ）が変わった。足されたときも列挙する |
| ファイルの変化 | base にあった生成物のファイルが、head に無い。削除と名前の変更を含む。base に 1 つも無く、head にあるとき（置き場の移動）も含む。`生成物ファイル(<名前>)` として列挙する |

新しい ID の行を足す変化は、規範のとおり、列挙しません。最初から `@pending` の新しい AC も、同じ扱いです。未解決の Blocking な OI に縛られるので、検査から外れる穴にならないためです（03 §3.4.2 の ② ③）。

#### 読む範囲

スクリプトが「ある」とみなす記述は、Kotlin の検査と同じにします。対象は `TrsTables.read`、`TestNameCheck`、`RequirementTraceCheck.scan` です。広く読むと、検査から外れた記述が、変化なしで素通りするためです。

| 記述 | 読む範囲 |
|---|---|
| 行 | `scan` を移植して読む。HTML コメントとコードブロックの中は、表にも見出しにもしない |
| US・AC・`C-xx` の行 | 見出しが完全に一致する表の中だけ。US の表、AC の 7 列の表、5.2 の 4 列の表である |
| UC の節 | 見出しから、次の同じ深さ以上の見出しまで。HTML コメントの行は除く |
| シナリオ | 言語が `gherkin` のコードブロックの中 |
| `@pending` | 本文全体。Kotlin と同じ正規表現で、コードブロックの外や HTML コメントの中も含む |

HTML コメントに入れた AC の行や、表の外に出した AC の行は、消えた ID として列挙されます。残る差は、どれも列挙が増える向きです。差は 3 つあります。

- Kotlin の検査が失敗にする記述（列数の違う行、見出しの違う表など）を、スクリプトは読み飛ばします。
- `gherkin` のシナリオも読みます。Kotlin の検査は、タグしか読みません。
- `@pending` は、全ファイルをまとめて判定します。Kotlin の検査は、ファイルごとに判定します。

#### 一度でも使った ID の集め方

base との差分だけでは、過去に消した ID が新しい行として戻る使い回しは見つかりません。集め方は、履歴と、削除の記録の 2 つがあります。

| 方式 | 見つかる ID | 欠点 |
|---|---|---|
| 履歴 | 置き場の履歴に、定義の行として現れた、すべての ID。定義の行は、表の先頭列、UC の見出し、`@AC-xx-yy` のタグ。US・UC・`C-xx` も含む | 全履歴の取得が要る |
| 削除の記録 | Open Issues の反映先に `AC-xx-yy 削除` と書いた AC | AC だけである。03 §5.4 の 5 で、未解決でない行が指さない AC は、記録なしで消せる |

履歴を主にしました。確実さが高いためです。削除の記録は、履歴の外にある ID を拾うために、足して使います。

- 履歴を集める置き場は、TRS の置き場と、移す前の置き場（`docs/testing/trs/`）です。`_` で始まるテンプレートは、ID の例なので除きます。
- ワークフローは、`actions/checkout` に `fetch-depth: 0` を付けます。履歴が浅いと、使い回しを検出できないので、スクリプトは失敗にします。

履歴にだけあり、いまの生成物に無い ID は、`AC-02-06`、`AC-03-09`、`C-01`、`C-02`、`C-03` です。これらを新しい行として足すと、使い回しとして失敗します。

- `AC-03-09` は、UC-03 の次の番号に当たります。次の再生成で、AC-03-09 を採番すると、失敗します。
- 再生成の入力には、これらの ID を採番しないことを渡します。採番では、履歴にある ID を避けます。
- 生成物の「AC-02-06 は使わない」の行は、手で直しません。採番しない ID の一覧は、TRS ファイルの 7.1 に置きました。再生成の入力として読みます。
- 次に採番する `AC-07-` は、履歴にありません。

#### PR 本文の理由の欄

PR 本文に `## 既存の ID の変化` の節を置き、列挙した ID ごとに 1 行ずつ書きます。

```markdown
## 既存の ID の変化

- AC-01-03: 要件の変更で、期待結果を C-52 に合わせて直した
- US-02, UC-02: 出典の要件 ID を足した
- Gherkin共通: Background を足した
- 生成物ファイル(TODO-001-task-management.md): 名前を変えた
```

- 書式は `- <ID>: <理由>` で、コロンは全角も可です。コンマで区切った複数の ID に、同じ理由を書けます。
- 理由が空、または `<理由>` のままの行は、理由なしとして失敗にします。
- 節が無い、または列挙した ID の行が無いときも、失敗にします。失敗のメッセージに、書くべき行の雛形を出します。
- 列挙しなかった ID の行は、失敗にしません。
- HTML コメントの中は、読みません。PR のテンプレートの記入例が、理由として読まれないためです。
- PR のテンプレートに、この節を足しました。変化が無いときは `なし` と書きます。

理由の中身が適切かは、機械で検査できません。人が PR でレビューします。CI が確かめるのは、変化を人に示すことと、理由が書かれていることです。

#### 自己テスト

`npm run lint` の `lint:id-changes` が、自己テストを実行します。コマンドは `node scripts/check-id-changes.mjs --self-test` です。

- 列挙しないもの: 変化なし、新しい AC の行・シナリオを足す変化、最初から `@pending` の新しい AC、空白だけの違い、行の並べ替え。
- 消えた ID: AC、US、UC、`C-xx` のそれぞれ。
- 変わった ID: AC の行、Examples の行、UC の節、US の行、`C-xx` の条件。既存の AC に足したシナリオと、シナリオだけが消えた AC も含む。コードブロックの中の表は数えない。
- `Gherkin共通`: `Background` の変更と追加、`Feature` の行の変更。
- `@pending` になった ID: 既存の AC、コードブロックの外の `@pending`、HTML コメントの中の `@pending`。外す向きは列挙しない。
- 使い回しの ID: 履歴の定義の行から集めた ID、削除の記録から集めた ID。base にある ID は、使い回しにしない。
- 読む範囲: 行を HTML コメントに入れる（AC、`C-xx`、UC の節）。AC の行を表の外に出す。AC の表の見出しを変える。
- 読む範囲: 見出しの先頭が `ID` でない US の表も、出典の列があれば読む。
- ファイルの変化: 削除、名前の変更、head が 0 件、base が 0 件。base にあるときの、新しいファイルの追加は列挙しない。
- 理由の欄: 理由があれば合格し、節がない、理由が空、`<理由>` のまま、HTML コメントの中、ほかの節、ID の形でない行は、理由なしになる。全角のコロンとコンマ区切りは読む。
- 一時的なリポジトリでの通し: 変化なし、使い回し（履歴にだけ残る ID と、削除の記録だけにある ID）、消えた AC、変わった AC、`@pending` になった AC。理由なしで失敗し、理由があれば通る。
- 一時的なリポジトリの失敗: base が先へ進んだときの merge-base、shallow、生成物のファイルが 0 件、AC の行が 0 件。

## 6. 特性化テストを作らない（03 §3.3）

このサンプルは、特性化テストを作らない。規範は「仕様書が存在しないレガシーコードに限り」特性化テストを作成してよいと定める。このサンプルには、要件定義書と TRS が先にあり、仕様書の無いコードが無い。

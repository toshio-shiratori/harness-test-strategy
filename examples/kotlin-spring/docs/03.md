# 03 TRS ガイドラインのサンプルでの実現（Kotlin + Spring Boot）

[03 TRS 策定ガイドライン](../../../docs/testing/03-trs-guideline.md)は言語中立の規範です。この文書は、そのうち Kotlin のサンプル（`examples/kotlin-spring/`）で規範をどう実現しているかを記録します。規範そのものは 03 を正とします。ここに書いた選択は、このサンプルの例であり、導入先に求めるものではありません。

## 1. TRS の配置（03 §1）

規範は「導入先の TRS ディレクトリに `<機能ID>-<機能名>.md` として置く」です。このサンプルでは次のとおりです。

| 対象 | 置き場所 |
|---|---|
| サンプルの TRS（ORD-001 / PAY-001 / PAY-002） | `examples/kotlin-spring/docs/trs/` |
| TRS のテンプレート | [`docs/testing/trs/_template.md`](../../../docs/testing/trs/_template.md)（標準の側） |

`TraceabilityTest` は `docs/trs/` の全 TRS を読み、テンプレートは `../../docs/testing/trs/_template.md` を読みます（`examples/kotlin-spring/` で実行するときの相対パス）。`build.gradle.kts` は、この 2 つを `./gradlew test` の入力にしています。

## 2. データ駆動テストへの展開（03 §2.3）

規範は「データ駆動テストに使う機能は、導入先が1つに決めて標準とする」です。このサンプルは Kotest の `withData` を標準にし、JUnit5 の `@ParameterizedTest` は採用していません。理由は次のとおりです。

- このリポジトリのテストは Kotest に統一されている。
- `@ParameterizedTest` には `junit-jupiter-params` の追加が必要で、実際に動かして検証できない例を書くことになる。

```kotlin
class PaymentTransitionTableTest : FunSpec({
    // 制約表の「条件」列（F1 × F2）。期待結果は制約表の値（C-22 は INVALID_TRANSITION で拒否）
    context("AC-02-06 終端状態からはどの操作でも遷移できない（C-22）") {
        withData(
            nameFn = { "${it.id} ${it.state::class.simpleName} × ${it.operation}" },
            ts = listOf(PaymentState.Captured(at), PaymentState.Failed(FailureReason.TIMEOUT)).flatMap { state ->
                listOf(authorize, capture, fail).map { op -> case("C-22", state, op) }
            },
        ) { it.apply(it.state) shouldBe rejected }
    }
})
```

全体は [`PaymentTransitionTableTest.kt`](../src/test/kotlin/com/example/payment/domain/PaymentTransitionTableTest.kt) にあります。[PAY-001](./trs/PAY-001-payment-state-transition.md) の制約表（§5.2）の C-20〜C-22 に対応します。Kotest 6.2.5 での実測で分かった点は次のとおりです。

- `withData` は `io.kotest.datatest.withData`。`kotest-runner-junit5` が持ち込む `kotest-framework-engine` に含まれ、追加の依存は要らない。
- `StringSpec` の `"名前" { }` の中に `withData` を置くと、「Nested withData is not supported inside StringSpec test bodies」で非推奨になる（`allWarningsAsErrors` によりビルドエラー）。AC 名のコンテナの下に置くには `FunSpec` の `context(...)` などを使う。
- 位置引数だけで呼ぶと `withData` のオーバーロードが曖昧になるため、`nameFn` / `ts` を名前付きで渡す。
- コンテナ名の先頭の AC ID は `TraceabilityTest` が文字列リテラルとして拾うので、検査側の変更は不要。

[ORD-001](./trs/ORD-001-add-item.md) は、因子同士の組合せ展開をしない理由を組合せ生成方針に書いた例です（テンプレート §4 の注記）。

## 3. トレーサビリティ検査の実装（03 §3.4）

規範の「トレーサビリティ検査」は、このサンプルでは `TraceabilityTest`（Konsist）が実装しています。`./gradlew test` で実行します。

### 3.1 テスト名の付け方

- Kotest の文字列名・JUnit のバッククォート名のどちらでもよく、grep で機械的に辿れる。
- JVM のバッククォート名は `[` `]` `:` `.` を使えないため、`AC-xx-yy` を括弧やコロンで囲まない（ORD-001 の検証で判明）。
- TRS のトレーサビリティ表には `テストクラス::テスト名` を書く。

### 3.2 検査の対象

| 検査 | サンプルでの実現 |
|---|---|
| AC に対応するテストの検査 | TRS の AC 表から `AC-xx-yy` を抽出し、`src/test`・`src/integrationTest`・`src/e2eTest` にその ID で始まるテスト名があるかを照合する。無ければ失敗させる |
| 未解決の Blocking な Open Issue の検査 | `UnresolvedBlockingCheck` が、TRS の Open Issues 表を読んで 03 §3.4 の条件を検査する。次のどれも失敗にする: 表の見出しが無い・行が無い・列数が合わない、区分・状態を分類できない(全行が対象)。関連列に AC が無い、範囲として読めない `〜` や逆順の範囲が残る、関連列の AC が AC 表に無い(未解決の Blocking の行だけが対象)。`@pending` に書けない値(`ISSUE-n`・表に無い ID・未解決の Blocking でない OI-ID・関連列に含まれない AC への付与)も失敗にする |
| テンプレートの検査 | `docs/testing/trs/_template.md` を同じ `UnresolvedBlockingCheck` に通す。テンプレートの未解決の Blocking（OI-001・OI-003）の AC には `@pending` が付いており、Open Issues 表は読める書式になっている |
| `AC-xx-yy` の重複 | `docs/trs/` の全 TRS の AC を集め、別の TRS が同じ ID を持てば失敗させる。照合はテスト全体のテスト名に対して行う |

### 3.3 AC の番号の割り当て（03 §3.4）

規範は「`xx` は TRS ごとに異なる番号を割り当て、新しい TRS は既存の TRS が使っていない最小の番号から採番する」です。このサンプルでは次のとおりです。

| TRS | `xx` |
|---|---|
| ORD-001 | `01` |
| PAY-001 | `02` |
| PAY-002 | `03` |

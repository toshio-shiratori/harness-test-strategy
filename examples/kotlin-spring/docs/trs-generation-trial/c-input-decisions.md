# オーナーの決定(Open Issues)

「状態」が Superseded の決定は、後の決定で改められた。有効なのは Resolved の決定である。

| ID | 論点 | 状態 | 決定内容 |
|---|---|---|---|
| OI-001 | 不正な入力の扱いをどう表すか（成功と拒否の判定方法、応答の形、理由の区分と表し方）。REQ-TODO-24・25 の成功の観測方法も含む。要件定義書の Q-19 | Resolved | 拒否は 400 で、本文は ProblemDetail（RFC 9457）に理由コードの配列 `codes` を足した形にする（順序は仕様にしない）。理由は 2 区分で、`TITLE_BLANK`（空・空白だけ・タイトル欠落）と `TITLE_TOO_LONG`（50 字超）。本文が JSON として読めないときは、同じ形で `MALFORMED_REQUEST`。成否は HTTP ステータスで判定し、成功は 2xx。REQ-TODO-24・25 の二重操作も 2xx で、内容は変わらない |
| OI-002 | タイトルの「Unicode の空白文字」の厳密な範囲は何か。要件定義書の Q-20 | Superseded（OI-016） | 空白は、Unicode の White_Space 属性を持つ文字すべて。U+200B・U+FEFF など、持たない文字は空白として扱わない |
| OI-003 | 期限を過ぎたタスク（完了済みを含む）は、「期限が近い順」のどこに並ぶか。要件定義書の Q-21 | Resolved | 期限の日付の昇順。期限切れは期限内より前に並ぶ。完了済みにも同じ規則を使う。現在時刻によらない |
| OI-004 | 50 字の数えは、前後の空白を除く前か後か | Resolved | 前後の空白を除いた後の長さを数える |
| OI-005 | 期限の入力形式、日付として不正な値の扱い、受け付ける日付の範囲は何か | Resolved | 入力は `YYYY-MM-DD` だけ。実在する暦日ならすべて受け付ける。それ以外（時刻つき、別形式、実在しない日）は 400 で `DUE_DATE_INVALID`。日付の範囲は定めない（案 i）ので、要件の追加は要らない。下限は、後に OI-015 で定めた |
| OI-006 | 存在しないタスクを完了にする、または未完了に戻そうとしたら、どうなるか | Resolved | 存在しないタスクを完了にする・未完了に戻す操作は 404 で、本文は ProblemDetail の `codes` に `TASK_NOT_FOUND`。範囲が増えるので、要件定義書に機能要件 REQ-TODO-33 を足した |
| OI-007 | 不正な入力の理由として、画面に表示する文言は何か（OI-001 の理由の区分に従う） | Resolved | 画面の理由の文言は、`TITLE_BLANK`「タイトルを入力してください」、`TITLE_TOO_LONG`「タイトルは 50 文字以内で入力してください」、`DUE_DATE_INVALID`「期限の日付が正しくありません」 |
| OI-008 | 書記素クラスタの判定は、どの規則と版に従うか。AC の例に含めてよい文字はどれか。タイトルを Unicode 正規化しない前提でよいか | Resolved | Unicode UAX #29 の拡張書記素クラスタに従う。Unicode 正規化はしない。AC の例は、結合文字と国旗に限る |
| OI-009 | 登録時刻が完全に同じタスクの間で、登録の新旧をどう決めるか。、登録時刻が異なる例だけを書く | Resolved | 登録ごとに増える番号を 2 番目の基準にする。登録時刻が同じなら、番号の小さい方を古いとする |
| OI-010 | 未完了・完了・期限切れを、画面にどう見せるか（手段と文言）。期限の日付を画面にどう見せるか。「完了」を文言として扱うか（REQ-TODO-23） | Resolved | 区分は、文言のラベル「未完了」「完了」「期限切れ」で表示する。期限は、一覧に `YYYY-MM-DD` の形で表示する |
| OI-011 | 複数の理由が同時にあるときの `codes` の中身と、0001-01-01・9999-12-31 の扱い | Resolved | 理由はすべて集めて `codes` に入れる。0001-01-01 と 9999-12-31 も、実在する暦日として受け付ける |
| OI-012 | 期限が空文字列のとき、存在しないタスクの識別子の形が不正なとき、0000 年の期限を受け付けるかを、どう扱うか。AC は足していない | Resolved | 期限の空文字列 `""` は 400 で `DUE_DATE_INVALID`（期限の項目を省くか null なら期限なし）。識別子の形が不正なとき（`/tasks/abc/complete`、`/tasks/abc/reopen`）は 404 で、本文は ProblemDetail の `codes` に `TASK_NOT_FOUND`（存在しないタスク OI-006 と同じ）。0000 年の期限は、実在する暦日として受け付ける。この論点は、OI-015 で改めた（0000 年の期限は拒否する） |
| OI-013 | JSON の型・形が定義と違う要求の扱い。タイトルに数値・真偽値・配列・オブジェクト、期限に数値などが来たとき、完了済みの表示の選択に未知の値が来たとき、定義にない項目が来たとき、どうなるか | Resolved | 型の自動変換はしない。タイトルに数値・真偽値・配列・オブジェクト、期限に数値などの、型や形が定義と違う本文は、400 で `codes` に `MALFORMED_REQUEST`（JSON として読めない本文と同じ扱い）。完了済みの表示の選択に未知の値は、400 で `MALFORMED_REQUEST`。定義にない項目は無視する |
| OI-014 | 登録に成功したとき、前の拒否の理由の表示と、入力欄の内容をどうするか。E2E のミューテーション確認で、どちらも AC が定めていないことに気づいた | Resolved | 登録に成功したら、前の拒否の理由の表示を消し、タイトルと期限の入力欄を空に戻す |
| OI-015 | OI-012 で受け付けると決めた 0000 年の期限のうち、閏日の 0000-02-29 は、ドメイン型（先発グレゴリオ暦で 0 年は閏年）では受理されるが、保存先の MySQL 8.4 の DATE 型が保存できず、登録が 500 で失敗する。0000-02-29 をどう扱うか（例: 保存形式を変えて受け付ける、閏日だけ拒否する、年の下限を定める） | Resolved | 期限の下限を 0001-01-01 にする。0000 年の期限は、400 で `DUE_DATE_INVALID` として拒否する。OI-012 の「0000 年の期限を受け付ける」を改める。範囲の規則なので、要件定義書に REQ-TODO-34 を足した |
| OI-016 | OI-002 は、空白を White_Space 属性を持つ文字に限り、U+200B・U+FEFF など表示されない文字を空白として扱わないと決めた。そのため U+200B だけのタイトルが 201 で登録され、一覧でタイトルが見えない行になる。このアプリにはタスクの編集も削除もなく、その行は消せない。NBSP だけのタイトルは拒否されるのに、U+200B だけは通る。表示されない文字だけのタイトルをどう扱うか | Superseded（OI-017） | 空白（White_Space）と、表示されない文字（Unicode の Default_Ignorable_Code_Point。U+200B・U+FEFF・U+2060・異体字セレクタなど）だけでできたタイトルは、400 と `TITLE_BLANK` で拒否する。表示される文字があるタイトルの前後や途中の表示されない文字（絵文字の組み立てに使う U+200D など）は、除かず、そのまま保存する。前後から除くのは、これまでどおり White_Space だけである。空白の範囲（White_Space）は OI-002 から変わらない。OI-002 の決定のうち、表示されない文字を空白として扱わない部分を改めた |
| OI-017 | OI-016 は、前後から除くのを White_Space だけにし、表示される文字があるタイトルの前後の表示されない文字は、除かず保存すると決めた。そのため、次の 2 つの境界が決まっていなかった。(a) 見た目が 50 字のタイトルの末尾に U+200B があると、51 字と数えて `TITLE_TOO_LONG` になる。(b) `[U+200B][半角空白]牛乳を買う` は、前後の空白の除去が U+200B で止まり、見える半角空白が先頭に残って保存される。タイトルの前後の表示されない文字をどう扱うか。前後から除く文字に、例外を設けるか。例外の文字は、どの位置まで残すか | Resolved | タイトルの両端から、空白（White_Space）と表示されない文字（Default_Ignorable_Code_Point）を除いてから、空の判定と字数の判定をし、除いた値を保存する。途中の空白と表示されない文字は、除かず、そのまま保存する。例外として、組になる文字は残す。組になる文字は、異体字セレクタ（Unicode の Variation_Selector 属性を持つ 260 個。U+180B〜180D、U+180F、U+FE00〜FE0F、U+E0100〜E01EF）と、タグ文字（U+E0020〜E007F の 96 個）で、合計 356 個である。残すのは、最後の表示される文字（空白でも表示されない文字でもない文字）の直後に続く、組になる文字の連なりだけである。先頭にあるもの、空白や除く文字の後ろにあるものは、作用する相手が無いので除く。先頭からは、最初の表示される文字より前をすべて除く。末尾からは、最後の表示される文字の直後に続く組になる文字の連なりを残し、その後ろをすべて除く。空の判定（空白と表示されない文字だけなら、400 と `TITLE_BLANK`）は変えない。組になる文字だけのタイトルも、空として拒否する。空白と表示されない文字の範囲は、OI-016 から変わらない。OI-016 の決定のうち、前後から除くのは White_Space だけで、表示される文字があれば前後の表示されない文字も保存する部分を改めた |

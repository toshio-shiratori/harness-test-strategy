# テスト品質の採点

導入先のリポジトリで、テスト実装の品質がテスト戦略の標準にどこまで沿っているかを、100 点満点で採点する。

- 配点は A(仕組み)50 点と B(テストの中身)50 点である。
- 何を満たせばよいかは、標準の節番号で参照する。このスキルは配点と判定の手順だけを持つ。
- 標準の規則の本文は書き写さず、判定に要る最小限の語だけを書く。
- 標準の節番号は「05 §5」のように、文書の番号と節で書く。文書は標準の `docs/testing/` にあたる置き場の、`01`〜`05` の方針書である。

## 1. 守ること

- 対象のコードを直さない。ソース、テスト、設定、文書を書き換えない。
- Issue、PR、コミットを作らない。
- 実行は検査モードで行い、自動修正のオプションを付けない。ビルドの出力ができるのはかまわない。
- 推測で点を付けない。証拠(ファイル、コマンド、結果)が無い項目は、未検証にする。
- 証拠があって判定が割れるものは、推測ではなく §8.4 の規則に従って扱い、割れたことを報告に印で示す。
- 同じ対象は、同じ規則で、同じ点になるよう採点する。AI の自由な判断に任せる範囲を、この文書の表と規則に限る。

## 2. 入力

利用者の指定を、次の 4 つの意味で読む。書式は、`target=<ディレクトリ>` のようなキーと値でも、自然文でもよい。

| 指定 | 意味 | 省略したとき |
|---|---|---|
| 対象 | 採点するディレクトリ | 作業ディレクトリ。報告に、対象として使ったパスを書く |
| 標準 | 標準(`docs/testing/` にあたるもの)の置き場。パスまたは URL | 次の探し方による |
| 全部を実行 | G3・G4・G5 も、導入先で実際に実行する | 実行しない(§5) |
| 出力先 | 報告を書くファイル | 会話にだけ出す。ファイルには書かない |

標準は、次の順に探す。

1. 標準の指定。
2. 対象の中の `docs/testing/`。
3. どちらにも無ければ、利用者に置き場を尋ねる。尋ねられない(非対話の)場合は、「標準が見つからない」と報告して止まる。点は付けない。

置き場が URL のときは、先にその URL を取得して、文書の一覧を得る。取得できなければ、利用者に尋ねる。尋ねられない場合は、上と同じく報告して止まる。

標準を見つけたら、このスキルが参照する節を実際に開く。節の見出しが標準に無いときは、版の食い違いの可能性があるので、その節を参照する項目を未検証にし、報告に理由を書く。

### 2.1 対象の外のファイル

対象がリポジトリの一部のとき(対象が、リポジトリのルートでないとき)は、次のファイルを、対象の外にあっても読む。

- リポジトリのルート、または CI のサービスが既定で読む置き場にある CI の定義。A3・A4・A9 の判定に使う。
- 同じ場所にある、還元先と完了条件を記録する場所の定義(PR・Issue のテンプレートやフォームなど)。A9 の判定に使う。

それ以外の、対象の外にあるファイルは読まない。コマンドとテストの置き場の特定にも、対象の外のファイルは使わない。

- リポジトリのルートを特定できないとき(対象にバージョン管理の情報が無いなど)は、対象の外に CI の定義や記録する場所の定義があるかを確かめられない。A9 を未検証にする。対象の中のファイルだけで A9 に段階を付けない。
- A9 以外の項目は、ルートを特定できないときも、対象の中のファイルだけで判定する。
- 対象の外から読んだファイルは、使った項目と一緒に、報告の「対象の外から読んだファイル」に書く(§9.2)。読まなかったときは「なし」と書く。

## 3. 手順

1. 入力を読み、標準の置き場を決める。
2. 対象の構成を調べる。調べるものは、ビルドの設定、対象の中の CI の定義、テストの置き場、ドメイン層、TRS、適用外の記録である。
3. 既定の実行として、G1 と G2 を実行する(§5)。全部を実行する指定があれば、G3〜G5 も実行する。
4. A の 9 項目を判定する(§7)。
5. B の抜き取りを決め、6 項目を判定する(§8)。
6. 未検証と適用外を整理し、合計と上限を出す(§6)。
7. 報告を出す(§9)。

## 5. 実行と証拠

### 5.1 何を実行するか

| 項目 | 既定の実行 | 全部を実行する指定 |
|---|---|---|
| A1 G1、A2 G2 | 導入先のビルドツールで実行する | 同じ |
| A3 G3、A4 G4 | 対象のコミットに対する CI の結果が読めれば、それを証拠にする。読めなければ未検証 | 実行する |
| A5 G5 | G2 の実行に含まれていれば、その結果を証拠にする。含まれていなければ、A3 と同じ | 実行する |
| A6〜A9、B1〜B6 | 実行しない。ファイルを読んで判定する | 同じ |

- 実行するコマンドは、ビルドの設定、README、対象の中の CI の定義から特定する。CI と同じコマンドを使う。コマンドとテストの置き場は、対象の中の定義だけで決める。
- コマンドは、ビルドの定義があるディレクトリに移ってから、定義どおりの形で実行する。別のディレクトリから、ディレクトリを指定するオプションを付けて実行する形に、書き換えない。
- 採点のために実行するコマンドは、ビルドのものに限らず、ファイルを読む・探すものも、1 つずつ単独で実行する。出力のファイルへの書き出し、ほかのコマンドとの連結、バックグラウンドでの実行を、足さない。
- 実行が拒まれたら、形を変えて試さない。その実行の結果を証拠にする項目を未検証にし、拒まれたコマンドを、報告の「未検証と適用外」の理由にそのまま書く。
- G2 は、層1専用のコマンドで実行する(02-2 §1.2)。専用のコマンドが無ければ、テスト全体のコマンドを実行する。層2に必要な環境が無くて実行できなければ、未検証にする。
- 各コマンドは 1 回だけ実行する。ランダムな入力を使うテストが失敗しても、再実行して結果を変えない。
- G5 が G2 の実行に含まれるかは、テストの実行結果に紐づけ検査のテスト名があるかで決める。
- G5 の検査が G2 に含まれる導入先では、紐づけ検査の失敗が A2 と A5 の両方に現れる。この二重の減点は、意図したものである。
- CI の結果が証拠になるのは、対象の HEAD のコミットに対する結果に限る。別のコミットの結果は使わない。CI の結果を読む手段は、導入先で使えるコマンドに任せる。
- 対象のディレクトリの中で、バージョン管理が無視しないファイルに、HEAD との違い(変更・追加・削除)が 1 つでもあるときは、CI の結果を使わない。
  - CI の結果を証拠にする項目は、すべて未検証にする。どの変更がどのゲートに効くかは、判断しない。
  - 対象の外の違いは、数えない。
  - 未検証にしたことと、違いのあるファイルを、報告の「未検証と適用外」の理由に書く。

### 5.2 証拠の書き方

証拠には、読んだファイル、実行したコマンド、結果の要点(成功・失敗の件数、スキップの件数、Mutation Score など)を書く。結果は、実行した出力から写す。覚えや推測で書かない。

## 6. 点の付け方

### 6.1 状況ごとの扱い

| 状況 | 扱い |
|---|---|
| 実行に必要な環境(ツール、ランタイム、コンテナ、ネットワーク)が無く、実行できない | 未検証 |
| CI の結果を読む手段が無い、または対象の HEAD の結果でない | 未検証 |
| 対象の中に、HEAD との違いのあるファイルがある(§5.1)。CI の結果を証拠にする項目だけ | 未検証 |
| コマンドの実行が拒まれた(§5.1) | 未検証 |
| リポジトリのルートを特定できない(A9 のみ。§2.1) | 未検証 |
| ドメイン層を特定できず、層の特定を要する観点がある(A6・A7 は §7、B3 は §8.3) | 未検証 |
| 実行して失敗した(テストの失敗、検査の違反、ビルドエラー) | 各項目の判定表で、失敗に当たる段階 |
| 仕組みが無い | 0 点 |
| 適用外で、05 §4.2 の 3 点(対象・理由・再評価のトリガー)と代替の担保の記録がある | 満点 |
| 適用外と主張するが、記録か代替の担保が無い | 0 点 |

- 適用外の記録は、対象の中の Markdown から探す。05 §5 の診断表の記入、導入の記録などが当たる。
- A5 の適用外は、表の満点の行に代えて、05 §4.1 の 3 つの条件をすべて満たすときに満点とする。
- 未検証は 0 点にする。項目の満点を、上限に足す。
- 項目の判定に要る条件が 1 つでも未検証なら、その項目全体を未検証にする。一部の条件だけで段階を付けない。

### 6.2 合計と上限

- 得点は、全項目の点の合計である。
- 上限は、得点に、未検証の項目の満点の合計を足した点である。
- 報告には、「72 点〔最大 86 点〕」のように書く。未検証が無ければ「86 点」とだけ書く。

## 7. A 仕組みの判定

各項目は、表の上から条件を確かめ、最初に当てはまる段階の点を付ける。点は整数で、端数処理はしない。B の点の付け方は §8.2 に別に定める。

| 項目 | 満点 | 半分 | 0 点 |
|---|---|---|---|
| A1 G1 静的検査 | 5 点: 型チェックと Lint の両方があり、実行してエラー 0 | 3 点: 一方だけがある。または、両方あってエラーが残るが、悪化のみを禁止する固定がある(05 §6) | 0 点: どちらも無い。または、エラーが残り、固定も無い |
| A2 G2 層1テスト | 8 点: 層1のテストが 1 件以上あり、全件成功し、数えるスキップが 0 件 | 4 点: 全件成功だが、数えるスキップが 1 件以上ある | 0 点: 1 件でも失敗する。層1のテストが 0 件 |
| A3 G3 ミューテーション | 8 点: 実行が設定され、Mutation Score が導入先の閾値以上。閾値が 02-2 §2.1 の値以上か、引き下げを承認した記録がある(下の A3 の承認の記録) | 4 点: 実行が設定されているが、閾値未満。または、閾値が 02-2 §2.1 より低く、承認の記録が無い | 0 点: 設定が無い |
| A4 G4 層2・実行境界 | 6 点: 条件 c1 と c2 の両方を満たす | 3 点: c1 か c2 の一方だけを満たす | 0 点: どちらも満たさない |
| A5 G5 TRS 整合 | 8 点: 条件 c1〜c3 をすべて満たす | 4 点: c1 を満たし、次のどちらか。c2 を満たすが c3 を満たさない。c2 を満たさないが c2′ と c3 を満たす | 0 点: 左のどちらでもない |
| A6 型ガードレール | 5 点: 観点 a〜c の違反が 0 件 | 3 点: 違反のある観点が 1 つ | 0 点: 違反のある観点が 2 つ以上 |
| A7 アーキテクチャ検査 | 3 点: 条件 d1 と d2 の両方を、テストとして実行する検査で強制している | 2 点: d1 か d2 の一方だけ | 0 点: どちらも無い |
| A8 テスト保護 | 4 点: テストの無効化を検出して失敗させる検査があり、層1・Integration・E2E のすべての置き場を対象にしている | 2 点: 検査はあるが、対象が一部の置き場だけ | 0 点: 検査が無い |
| A9 不具合還元 | 3 点: 条件 e1 と e2 の両方を満たす | 2 点: e1 か e2 の一方だけを満たす | 0 点: どちらも満たさない |

A2 のスキップは、テストの許可リストに載り、04 §3.4.1 の記録(理由と再有効化の期限)があるものを数えない。

A3 の猶予と記録は、次のとおり扱う。

- PR の評価軸をテストの強度にする猶予(05 §4.4.1)を使えるのは、補う手段と記録(05 §4.2 の 3 点)の両方があるときだけである。
- 使えるときは、満点の条件の「閾値以上」を、テストの強度で判定してよい。
- 全体実行の頻度を週次にする猶予は、記録があればよい。
- 承認の記録は、次の 2 つのどちらかがあれば、あるものとする。
  - 05 §3 ③ で確定したベースラインの記録。
  - 下の 4 つの場所にある、引き下げの承認の記録。

A3 の承認の記録を探す場所は、次の 4 つである。探す範囲は、対象の中と、§2.1 の対象の外のファイルである。

| 場所 | 証拠になる条件 |
|---|---|
| コードのコメント | 閾値の設定の根拠を述べた文がある |
| ADR | 引き下げの承認を述べた文がある |
| Issue・PR の回答 | 対象の中に、その文面のコピーがある |
| ファイルの責任者の承認を経た PR(例: CODEOWNERS) | 対象の中に、その承認を書き写した記録がある |

- コードのコメントは、承認済みの PR を経た変更の一部として扱う。PR は読まない。

閾値を現状値に固定し、悪化のみを禁止する方式は、02-2 §2.1 の「引き下げは人間の承認」による引き下げとして扱う。05 §3 ③ のベースラインの記録が無いときに限り、次の 2 つが上の場所に記録されていれば、満点の条件の「引き下げを承認した記録」を満たす。ベースラインの記録があるときは、この 2 つを問わず、承認の記録があるものとする。

1. 現状値と、その根拠。
2. 解消の期限と再評価のトリガー(05 §4.2)のうち、どちらか 1 つ。

2 つのうち 1 つでも記録が無ければ、この方式による承認の記録は無いものとして扱う。

条件の内容は次のとおり。

| 条件 | 内容 |
|---|---|
| c1(A4) | 層2(Integration・E2E)のテストが 1 件以上あり、全件成功する |
| c2(A4) | 層1と層2の置き場と実行コマンドが分かれ、層1にフレームワークやコンテナの起動を入れないことを、検査で確認している(02-2 §1.2) |
| c1(A5) | AC を持つ TRS が、対象にある |
| c2(A5) | 紐づけ検査が、03 §3.4 の表の「検査の単位」の行と ①〜⑪ の失敗条件を、すべて検査している(ID の書式は、下の「ID の書式の扱い」に従う) |
| c2′(A5) | 紐づけ検査が、03 §3.4 の ①・④・⑦ を、失敗条件にしている(c2 を満たさないときの段階に使う。ID の書式は c2 と同じ) |
| c3(A5) | 紐づけ検査を実行して通る |
| 観点 a(A6) | ドメイン層の公開された型・関数が、ドメインの値をプリミティブ型で持たない(02-1 §2.1 規則1)。02-2 §3.1 の 2 つの例外(値オブジェクトが内部に保持する値と定数、外部入力を一度だけパースする境界のファクトリ)は、違反に数えない。値オブジェクトのコンストラクタの引数と、内部に保持する値は、1 つ目の例外に含む |
| 観点 b(A6) | ドメイン型の生成が、検証付きの生成手段に限られる(02-1 §2.2 規則1) |

| e1(A9) | 04 §2.6 の項目と 04 §2.5 の完了条件が、ファイルで定義した記録の場所に含まれている(下の e1・e2 の判定) |
| e2(A9) | 完了条件(04 §2.5)の欄の欠落と未チェックの項目を検出して失敗する検査が、PR に対して走るよう、ファイルで定義されている(下の e1・e2 の判定) |

A3・A4・A9 の CI の定義と、A9 の記録する場所の定義は、対象の中と、§2.1 の範囲から探す。

条件や観点で段階を決める項目(A4〜A7・A9)は、次のとおり判定する。

- 条件ごとに、満たすか・満たさないか・未検証かと、根拠を、報告に必ず書く(§9.2)。
- ある条件を満たさないことは、ほかの条件を判定しない理由にならない。条件は、すべて判定してから、段階を付ける。
- A5 は、c3 を満たさないときも、c2 と c2′ を判定する。
- A5 を適用外とする主張は、AC を持つ TRS が対象に無いことを確かめたうえで、§6.1 による。
- 適用外の主張では、条件ごとの判定の表に、c1〜c3 に代えて 05 §4.1 の 3 つの条件を並べる。
- 条件 3 の実行と証拠は、§5.1 の A5 の行に従う。
- 条件 3 が未検証なら、§6.1 の最後の規則で A5 を未検証にする。

A5 の c2・c2′ と、B1・B4・B6 の違反の型では、ID の書式を、次のとおり扱う(以降「ID の書式の扱い」)。

- 別の書式は、03-1 §1 の 1 つ目と 2 つ目の条件を満たすときに、標準の書式と等価に扱う。
- 03-1 §1 の 3 つ目の条件は、等価の条件に含めない。A5 の c3 として判定し、未検証なら c3 だけを未検証にする。
- 等価な書式の ID は、紐づけ検査が、テスト名から ID として抽出する形である。
- 等価な書式では、1c・6a〜6c と 4c の手順 2 の「AC 番号」と位置の語を、次のとおり読む。
  - 「AC 番号」は、紐づけ検査が抽出した ID と読む。
  - 「先頭の」「名前に」は、その ID を、抽出する位置に持つと読む。
  - 「先頭に AC 番号を持たない」は、その ID を持たないと読む。
- A5 では、03-1 §1 の 1 つ目の条件を 03 §3.4 の ①、2 つ目を ⑦ として扱う。c2・c2′ のほかの失敗条件は、書式を問わず判定する。
- 抽出の規則(検査のコードや設定)と、2 つの条件の根拠を、報告の根拠に書く(§9.2)。

ドメイン層の特定を要するかは、観点ごとに次のとおり決まっている。

| 項目 | 観点 | 層の特定 | 理由 |
|---|---|---|---|
| A6 | a〜c | 要する | 抜き取る範囲が、ドメイン層だから |
| A7 | d1 | 要しない | 検査の有無だけで判定できるから |
| A7 | d2 | 要する | 検査が観点 a の対象を覆うかを見るから |

- ドメイン層は、層構成を示す文書、ディレクトリ名、アーキテクチャ検査の定義から特定する。
- 特定できなければ、利用者に尋ねる。
- 尋ねられなければ、「要する」観点を未検証にする。
- 「要しない」観点は、特定できなくても判定する。
- 未検証の観点がある項目は、§6.1 の最後の規則で、項目全体を未検証にする。

d2 は、次のとおり判定する。

- 検査が、観点 a の対象(ドメイン層の公開された型・関数で、例外を除いたもの)と、本番コード全体の既定分岐を検査しているかで判定する。
- 標準の例外(02-2 §3.1。観点 a が含むものと同じ)に沿った除外は、不足に数えない。
- 検査がどの構文まで見るか(関数の本文だけか、宣言も含むか、など)といった網羅の細部は、判定しない。

e1・e2 は、次のとおり判定する。

- e1 の記録の場所は、テンプレートやフォームなど、ファイルで定義したもので、形式は問わない。
- 記録の場所は、1 か所でも、複数に分けてもよい。合わせてすべての項目を含む。
- 04 §2.5 の完了条件は、各項目と 1 対 1 に対応する言い換えだけを認める。
- 04 §2.6 の項目は、1 項目を複数の欄に分けてよい。複数の項目を 1 つの欄にまとめるのは認めない。
- 自由に書けるだけの場所は、記録の場所に数えない。README などの説明文も、証拠にしない。
- 標準の置き場にある雛形(対象の中の標準の文書の写し)は、証拠にしない。記録するときに実際に使われる場所の定義だけを、証拠にする。
- e2 は、検査が必須のチェックかどうかを判定しない。
- 人のレビューの必須化だけでは、e2 を満たさない。
- ルートを特定できたうえで、ファイルの定義で確かめられない仕組みは、満たさない。

A6 は、ドメイン層の本番ソースを、次の規則で抜き取って判定する。

- 違反かどうかの判定は、コードの形だけで行う。README、設計書、コメントの説明を根拠に、違反を見逃さない。
- 違反に数えない例外は、観点 a に書いた 02-2 §3.1 の 2 つだけである。
- ドメイン層は、上の「層の特定を要するか」の表の下の規則(特定の方法、尋ねる手順、未検証)に従う。
- 抜き取りは、ドメイン層の本番ソースのファイルを、対象のルートからの相対パスのバイト順で昇順に並べ、先頭から 6 件とする(6 件に満たなければ全件)。
- 観点ごとに、違反のあるファイルを数える。1 件でもあれば、その観点は違反とする。

## 8. B テストの中身の判定

### 8.1 抜き取り

テストの置き場(層1・Integration・E2E)を、ビルドの設定、対象の中の CI の定義、ディレクトリ構成から特定する(02-2 §1.2)。置き場が分かれていなければ、テストのファイルを、02-2 §1.2 の表の「置くもの」の欄で、層1・Integration・E2E に分類する。

- 分類は、ファイルが使う依存と宣言で決める。実ブラウザを操作するものは E2E、コンテキストの起動かコンテナ(実 DB)を使うものは Integration、それ以外は層1とする。
- 分類した結果は、報告に書く。以降の「置き場」は、この分類を指す。

抜き取りの規則は、次のとおり。

- 抜き取りは、置き場ごとに行う。
- テストのファイルを、対象のルートからの相対パスのバイト順で昇順に並べる。m 件を 0 から番号付けし、i = 0〜5 について ⌊i × m ÷ 6⌋ 番のファイルを取る(6 件を等間隔に取る)。m が 6 以下なら全件を取る。
- テストのファイルは、テストを 1 件以上含むものとする。ジェネレータやフィクスチャなどの補助、ビルドの出力、依存物は数えない。
  - この判定では、Gherkin の Scenario と Scenario Outline を、それぞれテスト 1 件と数える。Examples の行は数えない。
- 仕組みの検査のテストは、m に数えず、抜き取りから除く。判定は、次の規則だけで行う。
  - 対象のルートからの相対パスを、パスの区切りで分けたディレクトリ名のどれかが、次の語のどれかと全体で一致する。大文字小文字は区別しない。ファイル名は見ない。
  - 語を一部に含むだけのディレクトリ名は、一致に数えない。例: mutations は、mutation に一致しない。
  - 語は、architecture、traceability、protection、mutation、executionboundary である。
  - 除外したファイルの一覧を、報告に必ず出す。
- 抜き取りは、1 回の採点で固定し、B1〜B6 で使い回す(B3 を除く)。最大 18 件である。
- 抜き取りが全体で 0 件なら、B の 6 項目は 0 点とし、理由を報告に書く。

### 8.2 判定の方法

抜き取ったファイルごとに、項目の「違反の型」(§8.4)に当たるものがあるかを確かめる。1 つでも当たれば、そのファイルは違反ファイルとする。判定が割れた型は、当たりに数えない(§8.4)。

項目の点は、違反ファイルの数 k と、その項目の抜き取りの件数 n から、次の式で決める。

- 項目の点 = 項目の満点 × (1 − k ÷ n)
- 小数第 1 位を四捨五入する。0.5 は切り上げる。
- 段階の名は、k が 0 なら「満点」、k が n と同じなら「0 点」、それ以外は「減点」とする。

| 満点 | n | k | 点 |
|---|---|---|---|
| 10 点 | 13 | 1 | 9 点 |
| 10 点 | 13 | 2 | 8 点 |
| 7 点 | 2 | 1 | 4 点 |

n が 0 のときは、式を使わない。違反 0 件として満点にし、理由を報告に書く。状態は「検証済み」と書く。

- B4 で、層2の置き場が無いとき。または、置き場はあるがテストのファイルが 0 件のとき。
- B3 で、対象が 0 件のとき。

ただし、抜き取りが全体で 0 件のときは、§8.1 の規則で 0 点にする。

B3 の n は取った対象の数、k は違反のある対象の数とする(違反ファイルを、対象に読み替える)。

### 8.3 判定の対象

| 項目 | n の対象 |
|---|---|
| B1・B2・B5・B6 | 抜き取りの全ファイル |
| B4 | 層2(Integration・E2E)の置き場の抜き取り。n が 0 になる条件は §8.2 |
| B3 | 次の規則で取る PBT の対象 |

B3 の対象は、種類 1〜3 に共通の次の前提で探す。

- 種類 1・2 を探す範囲は、本番のソースのうち、ドメイン層だけである。ドメイン層は、§7 の A6 で特定した範囲である。
- 種類 3 を探す範囲は、本番のソース全体である。永続化やシリアライズなど、境界の変換も対象にする(02-1 §3.1)。
- 数える関数は、ソースに書かれた関数とコンストラクタだけである。言語やコンパイラが自動で作る関数と、継承した関数は数えない。
- 数える関数は、可視性がその型かそのファイルに閉じていないものである。モジュールやパッケージの中だけで公開するものも数える。
- 型かファイルの中に閉じたもの(非公開)だけを、数えない。
- 関数が引数で受け取る形と、レシーバで受け取る形は、同じに扱う。
- ドメイン層を特定できず A6 が未検証のときは、種類 3 の探す範囲に関わらず、B3 を未検証にする。§6.1 の規則のとおりで、例外は作らない。
- 列挙の順は、対象を成り立たせた関数が出現する位置で決める。ファイルの相対パスのバイト順で昇順とし、同じファイルの中では出現の順とする。
- 関数が複数あるときは、最初に出現する関数の位置を使う。種類 3 は、組の 2 つの関数のうち先に出現するほうを使う。

次の 3 種を、この順に列挙し、種類ごとに先頭の 2 件を取る(最大 6 件)。種類は、コードの形で決める。

| 種類 | 定義 | 1 件の数え方 |
|---|---|---|
| 1 検証付きの生成手段を持つ型(02-1 §2.2) | 型のコンストラクタか、その型に属するファクトリの中に、入力の検査と不正値の拒否がある | 型 1 つ |
| 2 状態を表す型と遷移(02-1 §2.3) | 閉じた型 X を、X そのもの、または X を直接の項目として持つ型として受け取り、受け取った型と同じ型を返す関数がある | X 1 つ |
| 3 変換の往復 | 引数 1 つの関数で、型 A から型 B への変換と、B から A への変換が、同じ型か同じファイルにある。A と B は別の型 | 組 1 つ |

- 種類 1 の不正値の拒否は、例外を出すか、失敗を返すことである。
- 種類 1 の検査は、その型の生成の経路(コンストラクタか、その型に属するファクトリ)のどこかにあればよい。
- 種類 1 では、可視性の限定を、外から呼べる生成の入口があるかの判定にだけ使う。
- 種類 2 の「X を持つ型」は、X を直接の項目として持つ型に限る。推移的には数えない。
- 種類 2 では、値が無いことを許す型(null 許容など)を、元の型と同じ型に数えない。遷移でなく、検索や解決の関数を拾うのを避けるためである。
- 種類 3 では、戻り値が失敗を表す型で包まれていても、包まれた型として数える。往復では、変換の失敗も変換の一部だからである。
- 失敗を表す型は、値が無いことを許す型か、元の型を型引数に持ち成功と失敗の形を持つ閉じた型である。
- 種類 3 の関数は、引数が 1 つのものに限る。引数の数は、次のとおりに数える。
  - インスタンスのメソッドは、引数が無ければ、レシーバを引数 1 つとする。引数があれば、レシーバは数えない。
  - 同伴・静的の関数の所属先は、レシーバに数えない。
- 同じ型が複数の種類に当たるときは、先の種類だけで数える。種類 3 は組を 1 件とし、組に含まれる型は、この判定に使わない。
- 種類ごとに列挙した全件を、報告に出す(§9.2)。表には、可視性の列と、取ったかどうか(はい・いいえ)の列を付ける。可視性は、数える関数が非公開でないことの根拠である。種類 3 は、組の 2 つの関数の両方の可視性を書く。
- 点を出す前に、報告の表で「取った」が「はい」の行の数を数え、種類ごとの min(列挙した件数, 2) の合計と一致することを確かめる。一致しなければ、取り方を直す。n は、一致を確かめた後の「はい」の行の数である。

### 8.4 違反の型

| 項目 | 型 | 違反の内容 |
|---|---|---|
| B1 期待値の出所 | 1a | 期待値を作る式の中で、テスト対象の関数を呼んでいる(03 §3.2) |
| | 1b | 実装の出力をそのまま保存した値(スナップショット、貼り付けた出力)を期待値にし、03 §3.3 の 2 つの条件(`characterization` の明示と、現状であることのコメント)が揃っていない |
| | 1c | 名前に AC 番号を持つテストの期待値が、TRS のその AC の期待結果と食い違う(TRS が対象にあるときだけ判定する) |
| B2 アサーションの強さ | 2a | アサーションが無い。または、例外が出ないことの確認だけである |
| | 2b | 存在・非 null・件数・型の確認だけで、具体値で確かめられる結果を確かめていない |
| | 2c | 厳密一致にできる期待値を、部分一致・包含・範囲の確認で済ませている(04 §3.4) |
| | 2d | モックの呼び出しの回数や順序の確認が中心で、結果を確かめていない(02-2 §2.3) |
| B3 PBT の適用 | 3a | その対象を、生成した入力で検証する PBT が無い(02-1 §3.1) |
| | 3b | Property の分類(02-1 §3.2)が、テスト名にもコメントにも無い |
| | 3c | Property が、実装と同じ計算式で期待値を作っている(02-1 §3.3 規則5) |
| | 3d | シードを固定した Property をコミットしている(02-1 §3.3.1) |
| B4 層の配置・E2E 最小化 | 4a | E2E のテストが、02-3 §1.2 の「E2E に置いてはならないもの」の表の左列に当たる |
| | 4b | E2E のテストが、02-3 §1.1 の 4 領域のどれに当たるかを、識別子・名前・コメントから読み取れない |
| | 4c | Integration のテストのファイルが、同じ呼び出し先に対して、入力の値だけを変えて、結果(拒否の理由・並び・状態)を確かめている。対象の Integration のテスト全体で、同じ呼び出し先ごとに合算し、3 通り以上になれば当たる。1〜2 通りは当たらない。水準に対応づけた拒否の入力は、水準ごとの代表 1 つを数えない(03-2 §3 の GR3) |
| B5 独立性・決定性 | 5a | 現在時刻・乱数・環境の値を取る呼び出しの結果が、アサーションの期待値にそのまま入っている(01 §3)。PBT のランダムな入力生成は除く(02-1 §3) |
| | 5b | 実時間の待機(固定時間の待ち)で結果を待つ |
| | 5c | ほかのテストが作った状態(共有の可変状態、実行の順序)に依存する |
| | 5d | 層1のテストが、コンテキストの起動、コンテナ、実 DB を使う(02-2 §1.2) |
| | 5e | 失敗をリトライで隠す指定がある(02-3 §1.4) |
| | 5f | PBT の失敗をシードで再現できない設定がある。失敗時のシード出力の抑止(02-1 §3.3 規則3)に加えて、失敗したシードを保存・再利用する機能があるライブラリでは、その機能の無効化(02-1 §3.3.2) |
| B6 命名・可読性 | 6a | テスト名の先頭の AC 番号が、03-1 §1 の書式に従っていない。§7 の「ID の書式の扱い」で等価とした書式は除く |
| | 6b | テスト名の先頭の AC 番号が、TRS の AC の表に無い(TRS が対象にあるときだけ判定する) |
| | 6c | 先頭に AC 番号を持たないテストについて、名前にもコメントにも、AC に結び付かない理由の文が 1 文も無い。特性化テスト(03 §3.3)として明示したものは除く(05 §6 の (b))。TRS が対象にあるときだけ判定する |
| | 6d | 名前が、何を確かめるかを説明していない(連番、`test1` のような名前だけ) |

- 1a・4c・5a・6c は、次のコードの形で判定する(印の規則の例外。下の例外の箇条)。
  - 1a のテスト対象は、実際の値の側の本番の関数とコンストラクタである。
    - 最も外側の呼び出し(レシーバの連なりを含む)と、その引数の中で直接呼ぶもの。
    - 実際の値の側が変数のときは、その変数の初期化の式に、同じ規則を当てる。
    - 補助関数は、中までたどる。その中で呼ぶ本番の関数とコンストラクタも、テスト対象に含める。
    - 補助関数は、テストのソースの置き場にある関数・ジェネレータ・テスト用の実装である。ファイルをまたいでもよい。
    - テストが外部から呼ぶ入口(HTTP のエンドポイントなど)は、本番の関数として扱う。
  - 1a の期待値の側は、実際の値と比べる側の式である。
    - 変数は、初期化の式までたどる。
    - 補助関数は、中までたどる。本番の関数の内部の呼び出しは、たどらない。
  - 1a は、期待値の側で、テスト対象を呼んでいれば当たる。
    - データを保持するだけの型の除外は無い。
    - 両側で同じコンストラクタを呼ぶ形(既定値の比較など)も、当たる。
  - 4c の入力は、呼び出しの引数と、テストが呼び出しの前に用意したデータである。
  - 4c の呼び出し先は、確かめる結果を返した呼び出し(関数、エンドポイント)である。
    - 対象の Integration のテスト全体で、同じ呼び出し先ごとに、結果を合算する。
    - ループ、表、パラメータ化も含む。
    - 抜き取ったファイルは、合算で 3 通り以上になる呼び出し先の結果を 1 つでも確かめていれば、当たる。
  - 4c の結果の通り数は、次のとおり数える。
    - 理由の値を確かめる拒否は、理由の値ごとに 1 通りとする。
    - 理由を確かめない例外・失敗は、まとめて 1 通りとする。
    - 値が無い結果(見つからない)は、1 通りとする。
    - 並びの順序は、異なるものごとに 1 通りとする。
    - 状態・種別の値(02-1 §2.3。区分を含む)は、項目ごとに異なる値を数え、最も多い項目の数を、その呼び出し先の状態の通り数とする。
      - 本番でどう表していても数える。文字列などの表現でもよい。
      - 4c は、入力を変えて確かめた数を数える。同じ応答で確かめる項目を増やしても、数は増えない。
    - 同じ結果を確かめる複数の入力は、1 通りに数える。
  - 4c は、拒否の水準ごとの代表の入力を、数えない(03-2 §3 の GR3)。
    - 拒否の結果は、理由の値を確かめる拒否、理由を確かめない例外・失敗、値が無い結果(見つからない)である。
    - 入力は、次の順で、拒否の水準に対応づける。
      1. データ駆動のケース名の先頭に制約 ID(`C-xx`)があるとき、その `C-xx` の行(因子制約表)の「条件」列にある水準 ID を、候補とする。GR3 の「層2で実行する制約行」の代表も、これで対応づけられる。
      2. 1 に当たらないとき、テスト名(コンテナ名を含む)の先頭の AC 番号の根拠にある `C-xx` の行の、「条件」列にある水準 ID を、候補とする。
      3. 候補のうち、因子・水準の表で区分に「拒否」を含む水準を、拒否の水準とする。
         - 拒否の水準が 1 つだけなら、その水準に対応づける。
         - 複数あるときは、入力の値が当たる水準が 1 つだけなら、その水準に対応づける。
         - それでも 1 つに決まらないとき、または候補が無いとき(TRS が対象に無い、因子制約表が無い、`C-xx` も AC 番号も無い)は、「対応なし」とする。
    - `C-xx` の行と AC の根拠は、その `C-xx` や AC 番号を持つ TRS から探す。
    - 水準に対応づけた入力は、結果の通りではなく、入力の数で数える。上の「同じ結果を確かめる複数の入力は、1 通りに数える」は、当てない。
      - 入力の値が 1 つでも違えば、別の入力とする。同じ値の繰り返しは、1 つとする。
      - 呼び出し先と水準の組ごとに、入力の数から 1 を引く。最初の 1 つが代表である。2 つ目以降が、数える入力である。
    - 「対応なし」の拒否の結果は、通り数を上の規則どおりに数え、代表の分を引かない。
    - 呼び出し先の通り数は、次の 3 つの合計である。
      - 呼び出し先と水準の組ごとの、2 つ目以降の入力の数。
      - 「対応なし」の拒否の結果の通り数。
      - 並びの通り数と、状態の通り数(最も多い項目の数)。
  - 4c は、点を出す前に、報告の「4c の合算」の一覧(§9.2)で、当たりを決める。
  - 4c の趣旨は、層1で検証できること(01 §3)を、Integration で網羅させないことである。
    - 水準の代表を超えて、同じ水準の拒否を層2で重ねて確かめたものが、網羅に当たる。
    - 形に当たれば、層1で検証できるかは判定しない。
  - 5a の値を取る呼び出しは、実行環境の値を読む API そのものである。
    - 実際の時計、種を固定しない乱数、環境変数・システムプロパティなど、実行環境の設定を読む API。
    - 補助関数で包んでいても、中までたどる。
    - テストが値を決める時計(固定した時計、進める時計)は、含まない。
  - 5a の期待値は、実際の値と比べる側の式である。
    - 変数は、1a と同じく、初期化の式までたどる。
    - 取得した値が、計算で別の値に作り変えられずに入っていれば、当たる。
    - 型の変換と既定値の指定は、作り変えに数えない。
  - 6c の「理由の文」は、次のどちらかの文である。
    - そのテストが AC 以外の目的のためにあると述べた文。
    - AC に結び付けない旨を述べた文。
  - 6c では、何を確かめるかを言い換えただけの文を、理由の文に数えない。
  - 6c の理由の文を探す範囲は、次の 4 つである。どれかに理由の文があれば、当たらない。
    - テストの名前。
    - テストの直前のコメント。
    - テストを直接囲む単位(型・ブロック)の宣言の直前のコメント。
    - テストを含むファイルの先頭のコメント。ファイル内のすべてのテストに及ぶ。
  - 6c の「直前のコメント」は、宣言の前に連なるコメントの並びである。
    - 間の注釈・属性は、飛ばす。
    - 空行や、ほかの宣言があれば、そこで切れる。
  - 6c の「ファイルの先頭のコメント」は、次のどちらかのコメントである。
    - パッケージ・モジュール・取り込みの宣言より前にあるコメント。
    - 最初の宣言より前にあり、その宣言と空行で離れたコメント。
  - 6c の「最初の宣言」は、型・関数・ブロックなどの宣言の最初のものである。
    - パッケージ・モジュール・取り込みの宣言(例: package、import)は、含めない。
  - 最初の宣言の直前に、空行なしで続くコメントは、その宣言の範囲だけに及ぶ。
    - ファイル全体には及ばない。
  - 6c は、理由が妥当かどうかを判定しない。
- 1c・6b・6c は、TRS が対象に無いときは判定せず、判定しなかったことを報告に書く。
- B2 は、G3 の結果を読めたときに限り、次の規則で証拠を足す。
  - 抜き取ったテストのファイルから、名前の接頭辞・接尾辞(`test_`、Test、Spec など)を除いた名前の本番ファイルを、対象とする。同名の本番ファイルが無ければ、足さない。
  - 対象に生存ミュータントがあり、原因が「アサーション不足・弱い」(02-2 §2.2 の表)なら、そのテストのファイルを違反ファイルに数える。
  - 原因の判定は、生存ミュータントの行を実行する抜き取りのテストを読み、その結果を確かめるアサーションが無い、または 2a〜2d に当たる場合に限る。
  - 入力カバレッジ不足、等価ミュータント、デッドコードは数えない。
  - 足した結果の k は、n を超えない(抜き取り外のファイルは数えない)。
- 1 つのファイルで 1 つの型に複数回当たっても、違反ファイルは 1 件と数える。
- 違反の型の判定が割れるときは、その型を違反に数えない。根拠の行を示し、報告の「判定が割れた」の欄に印を付ける。数えないと点が甘くなる側に倒れるので、割れた型は報告に挙げる。
- 印は、証拠が揃っていて判定の目安(§8.5)でも決まらないときに付ける。証拠が無いときは、未検証にする。
- 1 つのファイルに、割れた型と割れていない型の両方があるときは、割れていない型だけで違反ファイルを決める。
- 印の規則の例外として、形で定義した型(1a・4c・5a・6c)は、判定が割れた型として扱わない。印を付けず、形に当たれば違反に数える。
  - 形に当たるかどうか迷うときも、当たりにする。
  - 6c の迷う文は、理由の文に数えず、当たりにする。
- 印の規則の例外として、ライブラリの挙動(マッチャの一致の範囲、既定の設定など)は、文書で確かめられなければ、違反に数えず、未検証にもしない。文書は、導入先に同梱された文書か、ライブラリの公式文書とする。確かめた手段と、判定しなかったことを、報告に書く。

### 8.5 判定の目安

判断の入る違反の型に、当たる例と当たらない例を示す。

| 型 | 当たる例 | 当たらない例 |
|---|---|---|
| 1a | 期待値を作る式の中で、テスト対象の関数を呼ぶ | 仕様の値をリテラルで書く。テスト対象でない関数だけで作る |
| 2a | アサーションが 1 つも無い。本体が空である | 例外が起きることの確認。起きなければテストが失敗するので、「例外が出ないことの確認だけ」に数えない |
| 2b | 結果が null でないことだけを確かめる | 生成した ID のように値が決まらない出力に、存在と形式を確かめる |
| 2c | 全文で一致させられる期待値を、「含む」の確認で済ませる | 順序を問わない全体の一致(集合としての一致)。PBT の不変条件 |
| 2d | モックの呼び出し回数の確認だけで終わる | 結果の確認に加えて、副作用の呼び出しも確かめる |
| 4a | E2E で、範囲外の入力を何通りも試す | 主要な正常系を 1 本通す。代表の異常系を少数だけ通し、残りは層1・Integration に任せる(網羅しない) |
| 4c | 1 つの拒否の水準に、入力を 4 つ確かめる(代表を除いて 3)。2 つの水準に入力を 3 つずつ確かめる(2 + 2 の 4)。水準に対応づけない拒否の理由を 3 通り以上確かめる。水準に対応づけない、見つからない・例外・状態の値の 3 つを確かめる | 拒否の水準ごとに代表の入力を 1 つずつ確かめる(水準が 3 つ以上あっても、当たらない)。1 つの水準に入力を 3 つ確かめる(代表を除いて 2)。合算で 2 通り以下の呼び出し先を、代表値で確かめる。別のファイルで 3 通り以上になる呼び出し先は、代表値で確かめていても当たる |
| 5a | 現在時刻を取得し、その値を期待値にそのまま入れる | 固定した時計を渡す。取得した値を期待値にそのまま入れない |
| 5c | 前のテストが作ったデータを読む。実行の順序を指定する | 各テストが自分で準備する。共有するのは読み取り専用の定数だけ |
| 6c | 名前にも、コメントにも、AC に結び付かない理由が無い | 理由の文が 1 文でもある |
| 6d | `test1`、`works`、連番だけの名前 | 対象と期待する結果が読み取れる名前 |

## 9. 報告

### 9.1 出し方

- 次の形の Markdown を、会話に出す。見出しの文字列は、そのまま使う。
- 出力先の指定があるときだけ、同じ内容をファイルにも書く。
- 項目の点数、段階、証拠、改善の提案は、すべての項目に書く。
- B の項目には、抜き取ったファイルごとの判定(当たった違反の型、または「なし」)と、根拠の行を必ず並べる。
- A の項目のうち、条件や観点で段階を決めるものは、§7 の条件ごとの判定を並べる。
- B3 の対象は、列挙した全件を一覧にする(§8.3)。対象の外から読んだファイルも、一覧にする(§2.1)。
- 改善の提案は、標準の節番号を添え、減点した項目だけに書く。満点の項目は「なし」とする。
- 項目は、配点表の順に書く。点の低い順に並べ替えない。
- 「項目別の採点」の表は、評価名を先に置き、ID(A1 など)を最後の列に置く。評価名は、§4 の項目名からゲート番号(G1 など)を除いたものにする。
- 「減点の主な理由」は、満点でない項目に 1 文で書く。満点の項目は「なし」とする。
- ただし、未検証の項目は「未検証: 」、適用外として満点にした項目(§6.1)は「適用外: 」から始め、点によらず理由を書く。
- 記録が無く 0 点にした適用外の主張は、満点でない項目なので、減点の理由を書く。「適用外: 」は付けない。

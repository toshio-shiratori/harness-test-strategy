# テスト品質の採点

導入先のリポジトリで、テスト実装の品質がテスト戦略の標準にどこまで沿っているかを、100 点満点で採点する。

- 配点は A(仕組み)50 点と B(テストの中身)50 点である。
- 何を満たせばよいかは、標準の節番号で参照する。このスキルは配点と判定の手順だけを持つ。
- 標準の規則の本文は書き写さず、判定に要る最小限の語だけを書く。
- 標準の節番号は「05 §5」のように、文書の番号と節で書く。文書は標準の `docs/testing/` にあたる置き場の、`01`〜`05` の方針書である。

## 1. 守ること

- 対象のコードを直さない。ソース、テスト、設定、文書を書き換えない。
- Issue、PR、コミットを作らない。
- 実行は検査モードで行い、自動修正のオプションを付けない。ビルドの出力ができるのはかまわない。
- 推測で点を付けない。証拠(ファイル、コマンド、結果)が無い項目は、未検証にする。
- 証拠があって判定が割れるものは、推測ではなく §8.4 の規則に従って扱い、割れたことを報告に印で示す。
- 同じ対象は、同じ規則で、同じ点になるよう採点する。AI の自由な判断に任せる範囲を、この文書の表と規則に限る。

## 2. 入力

利用者の指定を、次の 4 つの意味で読む。書式は、`target=<ディレクトリ>` のようなキーと値でも、自然文でもよい。

| 指定 | 意味 | 省略したとき |
|---|---|---|
| 対象 | 採点するディレクトリ | 作業ディレクトリ。報告に、対象として使ったパスを書く |
| 標準 | 標準(`docs/testing/` にあたるもの)の置き場。パスまたは URL | 次の探し方による |
| 全部を実行 | G3・G4・G5 も、導入先で実際に実行する | 実行しない(§5) |
| 出力先 | 報告を書くファイル | 会話にだけ出す。ファイルには書かない |

標準は、次の順に探す。

1. 標準の指定。
2. 対象の中の `docs/testing/`。
3. どちらにも無ければ、利用者に置き場を尋ねる。尋ねられない(非対話の)場合は、「標準が見つからない」と報告して止まる。点は付けない。

置き場が URL のときは、先にその URL を取得して、文書の一覧を得る。取得できなければ、利用者に尋ねる。尋ねられない場合は、上と同じく報告して止まる。

標準を見つけたら、このスキルが参照する節を実際に開く。節の見出しが標準に無いときは、版の食い違いの可能性があるので、その節を参照する項目を未検証にし、報告に理由を書く。

## 3. 手順

1. 入力を読み、標準の置き場を決める。
2. 対象の構成を調べる。調べるものは、ビルドの設定、CI の定義、テストの置き場、ドメイン層、TRS、適用外の記録である。
3. 既定の実行として、G1 と G2 を実行する(§5)。全部を実行する指定があれば、G3〜G5 も実行する。
4. A の 9 項目を判定する(§7)。
5. B の抜き取りを決め、6 項目を判定する(§8)。
6. 未検証と適用外を整理し、合計と上限を出す(§6)。
7. 報告を出す(§9)。

## 5. 実行と証拠

### 5.1 何を実行するか

| 項目 | 既定の実行 | 全部を実行する指定 |
|---|---|---|
| A1 G1、A2 G2 | 導入先のビルドツールで実行する | 同じ |
| A3 G3、A4 G4 | 対象のコミットに対する CI の結果が読めれば、それを証拠にする。読めなければ未検証 | 実行する |
| A5 G5 | G2 の実行に含まれていれば、その結果を証拠にする。含まれていなければ、A3 と同じ | 実行する |
| A6〜A9、B1〜B6 | 実行しない。ファイルを読んで判定する | 同じ |

- 実行するコマンドは、ビルドの設定、README、CI の定義から特定する。CI と同じコマンドを使う。
- G2 は、層1専用のコマンドで実行する(02-2 §1.2)。専用のコマンドが無ければ、テスト全体のコマンドを実行する。層2に必要な環境が無くて実行できなければ、未検証にする。
- 各コマンドは 1 回だけ実行する。ランダムな入力を使うテストが失敗しても、再実行して結果を変えない。
- G5 が G2 の実行に含まれるかは、テストの実行結果に紐づけ検査のテスト名があるかで決める。
- G5 の検査が G2 に含まれる導入先では、紐づけ検査の失敗が A2 と A5 の両方に現れる。この二重の減点は、意図したものである。
- CI の結果が証拠になるのは、対象の HEAD のコミットに対する結果に限る。別のコミットの結果は使わない。CI の結果を読む手段は、導入先で使えるコマンドに任せる。

### 5.2 証拠の書き方

証拠には、読んだファイル、実行したコマンド、結果の要点(成功・失敗の件数、スキップの件数、Mutation Score など)を書く。結果は、実行した出力から写す。覚えや推測で書かない。

## 6. 点の付け方

### 6.1 状況ごとの扱い

| 状況 | 扱い |
|---|---|
| 実行に必要な環境(ツール、ランタイム、コンテナ、ネットワーク)が無く、実行できない | 未検証 |
| CI の結果を読む手段が無い、または対象の HEAD の結果でない | 未検証 |
| 実行して失敗した(テストの失敗、検査の違反、ビルドエラー) | 各項目の判定表で、失敗に当たる段階 |
| 仕組みが無い | 0 点 |
| 適用外で、05 §4.2 の 3 点(対象・理由・再評価のトリガー)と代替の担保の記録がある | 満点 |
| 適用外と主張するが、記録か代替の担保が無い | 0 点 |

- 適用外の記録は、対象の中の Markdown から探す。05 §5 の診断表の記入、導入の記録などが当たる。
- 未検証は 0 点にする。項目の満点を、上限に足す。
- 項目の判定に要る条件が 1 つでも未検証なら、その項目全体を未検証にする。一部の条件だけで段階を付けない。

### 6.2 合計と上限

- 得点は、全項目の点の合計である。
- 上限は、得点に、未検証の項目の満点の合計を足した点である。
- 報告には、「72 点〔最大 86 点〕」のように書く。未検証が無ければ「86 点」とだけ書く。

## 7. A 仕組みの判定

各項目は、表の上から条件を確かめ、最初に当てはまる段階の点を付ける。点は整数で、端数処理はしない。

| 項目 | 満点 | 半分 | 0 点 |
|---|---|---|---|
| A1 G1 静的検査 | 5 点: 型チェックと Lint の両方があり、実行してエラー 0 | 3 点: 一方だけがある。または、両方あってエラーが残るが、悪化のみを禁止する固定がある(05 §6) | 0 点: どちらも無い。または、エラーが残り、固定も無い |
| A2 G2 層1テスト | 8 点: 層1のテストが 1 件以上あり、全件成功し、数えるスキップが 0 件 | 4 点: 全件成功だが、数えるスキップが 1 件以上ある | 0 点: 1 件でも失敗する。層1のテストが 0 件 |
| A3 G3 ミューテーション | 8 点: 実行が設定され、Mutation Score が導入先の閾値以上。閾値が 02-2 §2.1 の値以上か、引き下げを承認した記録がある | 4 点: 実行が設定されているが、閾値未満。または、閾値が 02-2 §2.1 より低く、承認の記録が無い | 0 点: 設定が無い |
| A4 G4 層2・実行境界 | 6 点: 条件 c1 と c2 の両方を満たす | 3 点: c1 か c2 の一方だけを満たす | 0 点: どちらも満たさない |
| A5 G5 TRS 整合 | 8 点: 条件 c1〜c3 をすべて満たす | 4 点: c1 を満たし、次のどちらか。c2 を満たすが c3 を満たさない。c2 を満たさないが c2′ と c3 を満たす | 0 点: 左のどちらでもない |
| A6 型ガードレール | 5 点: 観点 a〜c の違反が 0 件 | 3 点: 違反のある観点が 1 つ | 0 点: 違反のある観点が 2 つ以上 |
| A7 アーキテクチャ検査 | 3 点: 条件 d1 と d2 の両方を、テストとして実行する検査で強制している | 2 点: d1 か d2 の一方だけ | 0 点: どちらも無い |
| A8 テスト保護 | 4 点: テストの無効化を検出して失敗させる検査があり、層1・Integration・E2E のすべての置き場を対象にしている | 2 点: 検査はあるが、対象が一部の置き場だけ | 0 点: 検査が無い |
| A9 不具合還元 | 3 点: 条件 e1 と e2 の両方を満たす | 2 点: e1 か e2 の一方だけを満たす | 0 点: どちらも満たさない |

A2 のスキップは、テストの許可リストに載り、04 §3.4.1 の記録(理由と再有効化の期限)があるものを数えない。

A3 の猶予と記録は、次のとおり扱う。

- PR の評価軸をテストの強度にする猶予(05 §4.4.1)を使えるのは、補う手段と記録(05 §4.2 の 3 点)の両方があるときだけである。
- 使えるときは、満点の条件の「閾値以上」を、テストの強度で判定してよい。
- 全体実行の頻度を週次にする猶予は、記録があればよい。
- 承認の記録には、05 §3 ③ で確定したベースラインの記録も含める。

条件の内容は次のとおり。

| 条件 | 内容 |
|---|---|
| c1(A4) | 層2(Integration・E2E)のテストが 1 件以上あり、全件成功する |
| c2(A4) | 層1と層2の置き場と実行コマンドが分かれ、層1にフレームワークやコンテナの起動を入れないことを、検査で確認している(02-2 §1.2) |
| c1(A5) | AC を持つ TRS が、対象にある |
| c2(A5) | 紐づけ検査が、03 §3.4 の表の「検査の単位」の行と ①〜⑪ の失敗条件を、すべて検査している |
| c2′(A5) | 紐づけ検査が、03 §3.4 の ①・④・⑦ を、失敗条件にしている(c2 を満たさないときの段階に使う) |
| c3(A5) | 紐づけ検査を実行して通る |
| 観点 a(A6) | ドメイン層の公開された型・関数が、ドメインの値をプリミティブ型で持たない(02-1 §2.1 規則1)。02-2 §3.1 の 2 つの例外(値オブジェクトが内部に保持する値と定数、外部入力を一度だけパースする境界のファクトリ)は、違反に数えない |
| 観点 b(A6) | ドメイン型の生成が、検証付きの生成手段に限られる(02-1 §2.2 規則1) |
| 観点 c(A6) | 状態・種別が閉じた型で表され、分岐に既定分岐が無い(02-1 §2.3 規則1・3) |
| d1(A7) | ドメイン層がフレームワークに依存しないことを、検査している |
| d2(A7) | ドメイン層のプリミティブ型の露出と、本番コード全体の既定分岐を、検査している |
| e1(A9) | 不具合の記録の雛形(04 §2.6)と、バグ修正 PR の完了条件(04 §2.5)が、対象にある |
| e2(A9) | PR のテンプレートの強制や CI の検査など、完了条件の未達を止める仕組みがある |

A6 は、ドメイン層の本番ソースを、次の規則で抜き取って判定する。

- ドメイン層は、層構成を示す文書、ディレクトリ名、アーキテクチャ検査の定義から特定する。特定できなければ、利用者に尋ねる。尋ねられなければ、A6 を未検証にする。
- 抜き取りは、ドメイン層の本番ソースのファイルを、対象のルートからの相対パスのバイト順で昇順に並べ、先頭から 6 件とする(6 件に満たなければ全件)。
- 観点ごとに、違反のあるファイルを数える。1 件でもあれば、その観点は違反とする。

## 8. B テストの中身の判定

### 8.1 抜き取り

テストの置き場(層1・Integration・E2E)を、ビルドの設定、CI の定義、ディレクトリ構成から特定する(02-2 §1.2)。置き場が分かれていなければ、テストのファイルを、02-2 §1.2 の表の「置くもの」の欄で、層1・Integration・E2E に分類する。

- 分類は、ファイルが使う依存と宣言で決める。実ブラウザを操作するものは E2E、コンテキストの起動かコンテナ(実 DB)を使うものは Integration、それ以外は層1とする。
- 分類した結果は、報告に書く。以降の「置き場」は、この分類を指す。

抜き取りの規則は、次のとおり。

- 抜き取りは、置き場ごとに行う。
- テストのファイルを、対象のルートからの相対パスのバイト順で昇順に並べる。m 件を 0 から番号付けし、i = 0〜5 について ⌊i × m ÷ 6⌋ 番のファイルを取る(6 件を等間隔に取る)。m が 6 以下なら全件を取る。
- テストのファイルは、テストを 1 件以上含むものとする。ジェネレータやフィクスチャなどの補助、ビルドの出力、依存物は数えない。
- 仕組みの検査のテストは、m に数えず、抜き取りから除く。判定は、次の規則だけで行う。
  - 対象のルートからの相対パスの、ディレクトリ名のどれかが、次の語のどれかを含む。大文字小文字は区別しない。ファイル名は見ない。
  - 語は、architecture、traceability、protection、mutation、executionboundary である。
  - 除外したファイルの一覧を、報告に必ず出す。
- 抜き取りは、1 回の採点で固定し、B1〜B6 で使い回す(B3 を除く)。最大 18 件である。
- 抜き取りが全体で 0 件なら、B の 6 項目は 0 点とし、理由を報告に書く。

### 8.2 判定の方法

抜き取ったファイルごとに、項目の「違反の型」(§8.4)に当たるものがあるかを確かめる。1 つでも当たれば、そのファイルは違反ファイルとする。

違反ファイルの数 k と、その項目の抜き取りの件数 n で、段階を決める。

| 段階 | 条件 | 10 点の項目 | 8 点の項目 | 7 点の項目 |
|---|---|---|---|---|
| 満点 | k が 0 | 10 点 | 8 点 | 7 点 |
| 上 | k が 1 以上で、k × 4 ≤ n | 7 点 | 6 点 | 5 点 |
| 中 | 上でなく、k × 2 ≤ n | 4 点 | 3 点 | 3 点 |
| 0 点 | 上のどれでもない | 0 点 | 0 点 | 0 点 |

n が 6 のときは、k が 1 で「上」、k が 2〜3 で「中」、k が 4 以上で「0 点」になる。n が 12 のときは、k が 1〜3 で「上」、4〜6 で「中」になる。n が 18 のときは、k が 1〜4 で「上」、5〜9 で「中」になる。

### 8.3 判定の対象

| 項目 | n の対象 |
|---|---|
| B1・B2・B5・B6 | 抜き取りの全ファイル |
| B4 | 層2(Integration・E2E)の置き場の抜き取り。層2の置き場が無ければ、違反 0 件として満点 |
| B3 | 次の規則で抜き取る PBT の対象 |

B3 の対象は、本番ソースから次の 3 種を、この順に列挙し、種類ごとに先頭の 2 件を取る(最大 6 件)。

1. 検証付きの生成手段を持つドメイン型(02-1 §2.2)
2. 状態を表す型と、その遷移を行う関数(02-1 §2.3)
3. 変換の往復(エンコードとデコードなど)を持つ組

- 列挙の順は、ファイルの相対パスのバイト順で昇順とし、同じファイルの中では出現の順とする。
- 対象が 0 件なら、B4 と同じく違反 0 件として満点にし、理由を報告に書く。

### 8.4 違反の型

| 項目 | 型 | 違反の内容 |
|---|---|---|
| B1 期待値の出所 | 1a | 期待値を、実装と同じ計算式や同じ関数の呼び出しで作っている(03 §3.2) |
| | 1b | 実装の出力をそのまま保存した値(スナップショット、貼り付けた出力)を期待値にし、03 §3.3 の 2 つの条件(`characterization` の明示と、現状であることのコメント)が揃っていない |
| | 1c | 名前に AC 番号を持つテストの期待値が、TRS のその AC の期待結果と食い違う(TRS が対象にあるときだけ判定する) |
| B2 アサーションの強さ | 2a | アサーションが無い。または、例外が出ないことの確認だけである |
| | 2b | 存在・非 null・件数・型の確認だけで、具体値で確かめられる結果を確かめていない |
| | 2c | 厳密一致にできる期待値を、部分一致・包含・範囲の確認で済ませている(04 §3.4) |
| | 2d | モックの呼び出しの回数や順序の確認が中心で、結果を確かめていない(02-2 §2.3) |
| B3 PBT の適用 | 3a | その対象を、生成した入力で検証する PBT が無い(02-1 §3.1) |
| | 3b | Property の分類(02-1 §3.2)が、テスト名にもコメントにも無い |
| | 3c | Property が、実装と同じ計算式で期待値を作っている(02-1 §3.3 規則5) |
| | 3d | シードを固定した Property をコミットしている(02-1 §3.3.1) |
| B4 層の配置・E2E 最小化 | 4a | E2E のテストが、02-3 §1.2 の「E2E に置いてはならないもの」の表の左列に当たる |
| | 4b | E2E のテストが、02-3 §1.1 の 4 領域のどれに当たるかを、識別子・名前・コメントから読み取れない |
| | 4c | Integration のテストが、層1で検証できること(値の妥当性、計算、状態遷移の分岐。01 §3)を中心にしている |
| B5 独立性・決定性 | 5a | 現在時刻・乱数・環境の値を固定せずに使い、結果がそれに依存する(01 §3)。PBT のランダムな入力生成は除く(02-1 §3) |
| | 5b | 実時間の待機(固定時間の待ち)で結果を待つ |
| | 5c | ほかのテストが作った状態(共有の可変状態、実行の順序)に依存する |
| | 5d | 層1のテストが、コンテキストの起動、コンテナ、実 DB を使う(02-2 §1.2) |
| | 5e | 失敗をリトライで隠す指定がある(02-3 §1.4) |
| | 5f | PBT の失敗をシードで再現できない設定がある。失敗時のシード出力の抑止(02-1 §3.3 規則3)に加えて、失敗したシードを保存・再利用する機能があるライブラリでは、その機能の無効化(02-1 §3.3.2) |
| B6 命名・可読性 | 6a | テスト名の先頭の AC 番号が、03-1 §1 の書式に従っていない |
| | 6b | テスト名の先頭の AC 番号が、TRS の AC の表に無い(TRS が対象にあるときだけ判定する) |
| | 6c | 先頭に AC 番号を持たないテストが、技術的な不変条件であることを名前かコメントで明記していない。特性化テスト(03 §3.3)として明示したものは除く(05 §6 の (b))。TRS が対象にあるときだけ判定する |
| | 6d | 名前が、何を確かめるかを説明していない(連番、`test1` のような名前だけ) |

- 1c・6b・6c は、TRS が対象に無いときは判定せず、判定しなかったことを報告に書く。
- B2 は、G3 の結果を読めたときに限り、次の規則で証拠を足す。
  - 抜き取ったテストのファイルから、名前の接頭辞・接尾辞(`test_`、Test、Spec など)を除いた名前の本番ファイルを、対象とする。同名の本番ファイルが無ければ、足さない。
  - 対象に生存ミュータントがあり、原因が「アサーション不足・弱い」(02-2 §2.2 の表)なら、そのテストのファイルを違反ファイルに数える。
  - 原因の判定は、生存ミュータントの行を実行する抜き取りのテストを読み、その結果を確かめるアサーションが無い、または 2a〜2d に当たる場合に限る。
  - 入力カバレッジ不足、等価ミュータント、デッドコードは数えない。
  - 足した結果の k は、n を超えない(抜き取り外のファイルは数えない)。
- 1 つのファイルで 1 つの型に複数回当たっても、違反ファイルは 1 件と数える。
- 違反の型の判定が割れるときは、当たると記録し、根拠の行を示し、報告の「判定が割れた」の欄に印を付ける。
- 印は、証拠が揃っていて判定の目安(§8.5)でも決まらないときに付ける。証拠が無いときは、未検証にする。

### 8.5 判定の目安

判断の入る違反の型に、当たる例と当たらない例を示す。

| 型 | 当たる例 | 当たらない例 |
|---|---|---|
| 1a | 期待値を、テスト対象と同じ関数で計算する | 仕様の値をリテラルで書く。独立した単純な手順で作る |
| 2b | 結果が null でないことだけを確かめる | 生成した ID のように値が決まらない出力に、存在と形式を確かめる |
| 2c | 全文で一致させられる期待値を、「含む」の確認で済ませる | 順序を問わない全体の一致(集合としての一致)。PBT の不変条件 |
| 2d | モックの呼び出し回数の確認だけで終わる | 結果の確認に加えて、副作用の呼び出しも確かめる |
| 4a | E2E で、範囲外の入力を何通りも試す | 主要な正常系を 1 本通す |
| 4c | Integration で、計算の分岐を入力を変えて網羅する | 配線や契約の確認に、代表値を使う |
| 5a | 現在時刻を取得して、期待値を作る | 固定した時計を渡す |
| 5c | 前のテストが作ったデータを読む。実行の順序を指定する | 各テストが自分で準備する。共有するのは読み取り専用の定数だけ |
| 6d | `test1`、`works`、連番だけの名前 | 対象と期待する結果が読み取れる名前 |

## 9. 報告

### 9.1 出し方

- 次の形の Markdown を、会話に出す。見出しの文字列は、そのまま使う。
- 出力先の指定があるときだけ、同じ内容をファイルにも書く。
- 項目の点数、段階、証拠、改善の提案は、すべての項目に書く。
- B の項目には、抜き取ったファイルごとの判定(当たった違反の型、または「なし」)と、根拠の行を必ず並べる。
- 改善の提案は、標準の節番号を添え、減点した項目だけに書く。満点の項目は「なし」とする。
- 項目は、配点表の順に書く。点の低い順に並べ替えない。

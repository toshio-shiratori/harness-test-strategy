## 5. E2E 最小化原則

E2E は遅く、壊れやすく、原因の切り分けが難しい。**E2E でしか検証できないものだけ**を E2E にする。

下層の Integration（HTTP/JSON の境界、ステータス・エラー形式、JSON ⇔ DTO 変換）の実例は `OrderControllerHttpTest`（`@WebMvcTest` + `RestTestClient`、Web スライスのみ起動。`src/integrationTest`）を参照する。これらは E2E にしない。

E2E の実例は [5.5](#55-実例-注文追加フォームの-e2e) の `OrderFormE2eTest`（`src/e2eTest`）を参照する。

### 5.1 E2E として許可する4領域

| # | 領域 | 識別子（`@e2e:<領域>`） | 内容 | 例 |
|---|---|---|---|---|
| 1 | **表示** | `display` | 実ブラウザでの描画・レイアウト・表示状態の確認（視覚回帰を含む） | 主要画面が崩れず描画される |
| 2 | **通信** | `communication` | フロント〜バックエンド〜DB 間の実配線の疎通 | ログイン API が実環境で往復できる |
| 3 | **主要ハッピーパス** | `happy-path` | 事業上クリティカルなユーザーフローの正常系（1機能につき原則1〜数本） | 商品選択 → 購入完了 |
| 4 | **実ブラウザ操作** | `browser-operation` | 実ブラウザでなければ再現できない挙動 | ドラッグ&ドロップ、ファイル選択、フォーカス/IME、ブラウザ履歴 |

### 5.2 E2E に置いてはならないもの

| 禁止対象 | 置くべき層 |
|---|---|
| 入力バリデーションの網羅（境界値・異常系） | 層1（Unit / PBT） |
| ビジネスロジックの分岐・計算の検証 | 層1 |
| エラーメッセージ文言の網羅 | 層1／コンポーネントテスト |
| 権限・状態遷移の組合せ網羅 | 層1（sealed 型＋PBT）／層2 Integration |
| 異常系・例外系の網羅 | 層1／層2 Integration |

### 5.3 E2E 追加時の審査

E2E を新規追加する PR には次を記載し、レビューで確認する。

- [ ] 上記4領域のどれに該当するか
- [ ] 下層（層1・Integration）で代替できない理由
- [ ] 対応する TRS の AC 番号
- [ ] 想定実行時間と、不安定要因（待機・外部依存）への対策

### 5.4 E2E 予算

- E2E の総実行時間に上限（例: PR パイプライン内で 10 分以内）を設け、超過時は 04 §4 の破棄基準で見直す。
- flaky なE2E は検出後 **即座に隔離（quarantine）** し、期限内に修復か破棄を決める。リトライで隠蔽しない。
- 実測と予算の対比は [02b §4.1](./02b-execution-and-mutation.md#41-適用タイミングと閾値) の「仮置きの値の見直し」に記録している。CI の `e2e` ジョブは `timeout-minutes: 10` でこの予算を上限にしている。

### 5.5 実例: 注文追加フォームの E2E

実例は `OrderFormE2eTest`（`src/e2eTest`）。対象 UI は `src/main/resources/static/index.html` の注文追加フォームで、Spring を `RANDOM_PORT` で起動し、Playwright の Chromium（ヘッドレス）で操作する。TRS は `ORD-001` で、AC を決めるのは下層と同じ TRS である。実行は `./gradlew e2eTest`、CI は `kotlin-samples.yml` の `e2e` ジョブ（セットアップは README の「E2E のセットアップ」）。

3 本は、5.1 の 4 領域のうち次の 3 領域に当たる。残る「実ブラウザ操作」に当たるテストはまだ無い。

| テスト | 領域 | 対応する AC | TRS のタグ | 見ているもの |
|---|---|---|---|---|
| `AC-01-04 有効な SKU と数量を送信すると、…HTTP 204 が表示される` | 主要ハッピーパス | AC-01-04 | `@e2e:happy-path` | 入力して送信すると、結果欄の `data-state` が `success` になり、ステータス 204 が表示される |
| `AC-01-09 範囲外の数量を送信すると、…OUT_OF_RANGE が表示される` | 通信 | AC-01-09 | `@e2e:communication` | ブラウザが組み立てた POST 要求（メソッド・`Content-Type`・JSON 本文）がサーバーに届き、応答の `codes` が画面に戻る |
| `AC-01-12 SKU が空白で数量が範囲外のとき、…codes が 2 件描画される` | 表示 | AC-01-12 | `@e2e:display` | 複数の `codes` が 1 件ずつ別の項目として描画され、`data-state` が `error` になる |

同じ AC を下層でも検証している（AC-01-04 は層1と Integration、AC-01-09 は Integration、AC-01-12 は層1と Integration）。E2E は、下層で確かめられない部分（ブラウザでの入力値の取得、要求の組み立て、応答の描画）だけを見る。範囲外の数量や空白の `sku` の網羅は、5.2 のとおり下層に任せている。

これらのテストは、5.3 の審査記載の見本でもある。各テストの KDoc に、5.3 の 4 項目（領域、下層で代替できない理由、AC 番号、想定実行時間と不安定要因への対策）を書いている。新しい E2E を足す PR は、この書き方に倣って PR 本文に記載する。

期待値の出所について。HTTP ステータスと `codes` の値は ORD-001 の AC（OI-003・OI-005・OI-006 で人間が確定）による。一方、結果欄の状態（`data-state`）、`codes` の `<li>` 表示、ステータス表示は、TRS 上の出所が無い。現状は画面の設計を暫定の正とし、ORD-001 の OI-007 に起票している。画面の AC を足すかは人間が決める。

## 1. 基本理念

1. **品質は「後から見つける」ものではなく「先に作り込む」もの**とする。誤りは、書けない（型）→ 即座に落ちる（Unit/PBT）→ 結合で落ちる → 探索で見つかる、の順に検出が遅くなりコストが増える。可能な限り上流・高速な層で止める。
2. **AIは高速に大量の変更を生む。** 人間のレビュー速度に依存した品質保証は成立しないため、機械的に検証可能なガードレール（テストハーネス）を品質の主軸とする。
3. **期待値の正は人間が合意した仕様にある。** AIが既存コードから期待値を逆生成してはならない（詳細は 03）。
4. **テストは資産であると同時に負債である。** 価値の低いテストは削除する。ただし削除は手順（04）に従う。

## 2. W字モデル（W-Model）の採用

開発ラインとテストラインを要件定義の段階から**並行**で進める。テストは実装後の工程ではない。

```mermaid
flowchart LR
  subgraph DEV["開発ライン"]
    direction LR
    D1["要件定義"] --> D2["基本設計"] --> D3["詳細設計"] --> D4["実装"] --> D5["CI・リリース判定"]
  end
  subgraph TEST["テストライン（並行）"]
    direction LR
    T1["TRS定義<br/>(US/UC)"] --> T2["受入条件(AC)確定"] --> T3["因子・水準設計"] --> T4["テスト実装(AI)"] --> T5["実行・探索"]
  end
  D1 <-.-> T1
  D2 <-.-> T2
  D3 <-.-> T3
  D4 <-.-> T4
  D5 <-.-> T5
  T3 -. "Open Issues で仕様を往復" .-> D2
```

| フェーズ | 開発ライン | テストライン（並行成果物） | 主担当 |
|---|---|---|---|
| 要件定義 | US/UC の策定 | TRS 仕様レイヤーの起草（AC を Gherkin で記述） | 人間（合意）／AI（起草支援） |
| 設計 | 型・ドメインモデル設計 | 因子・水準・因子制約の設計、Open Issues の起票 | 人間（型設計）／AI（網羅案） |
| 実装 | 実装 | Unit / PBT / Integration / E2E の生成 | AI（生成・修復）／人間（レビュー） |
| 検証 | CI 実行・リリース判定 | 探索的テスト、AIブラウザ操作エージェント | 人間＋AI |
| 運用 | 不具合対応 | 不具合還元（04 の Shift-Left Protocol） | AI（分析）／人間（承認） |

**運用ルール**

- TRS が存在しない機能は実装に着手しない（軽微な修正は例外とし、PR に理由を記載する）。
- 仕様の曖昧さは実装時に AI が推測で埋めず、TRS の Open Issues に起票して人間が決定する。

## 3. 3層アーキテクチャ

テストを実行速度とフィードバックの性質で3層に分け、**下の層ほど厚く、上の層ほど薄く**する。

```mermaid
flowchart TB
  L3["層3: 探索・発見層<br/>人間の探索的テスト / AIブラウザ操作エージェント<br/>（少・遅・高コスト）"]
  L2["層2: 結合・実環境層<br/>Integration / ハッピーパス厳選E2E（CI自動実行）"]
  L1["層1: 最速・確定層<br/>型システム / Lint / Unit / PBT<br/>（多・速・低コスト）"]
  L1 -- "未知の不具合を発見" --> L2
  L2 --> L3
  L3 -. "不具合還元（Shift-Left）" .-> L1
```

### 層1: 最速・確定層

| 項目 | 内容 |
|---|---|
| 構成 | 型システム、Lint、Unit テスト、PBT（Property-Based Testing） |
| フィードバック | ミリ秒〜数秒。エディタ保存時・コミット前フックで実行 |
| 判定 | 決定的（flaky を許容しない） |
| AIとの関係 | **AIによるコード自動修正の主軸。** AI は失敗出力を入力にして自己修復ループを回す |
| 方針 | ビジネスロジック・検証ロジック・状態遷移の検証は原則ここで完結させる |

### 層2: 結合・実環境層

| 項目 | 内容 |
|---|---|
| 構成 | Integration テスト（DB・外部I/F・API 契約）、ハッピーパスに厳選した E2E |
| 実行 | CI で全 PR に対し自動実行 |
| 方針 | 層1で検証できないもの（配線、通信、実ブラウザ依存）に限定する。E2E の許可領域は 02c §5 に従う |

### 層3: 探索・発見層

| 項目 | 内容 |
|---|---|
| 構成 | 人間の探索的テスト、AIブラウザ操作エージェントによる自律探訪 |
| 実行 | バックグラウンドで自律実行（夜間・デプロイ後など）。PR のブロッキング条件にはしない |
| 目的 | **仕様化されていない未知の不具合**の発見 |
| 出口 | 発見した不具合は 04 の不具合還元プロトコルで層1へ還元する。層3は「発見」で終わらせず「再発防止の下層化」まで行う |

### 3層の使い分け基準

| 検証したいこと | 置く層 |
|---|---|
| 値の妥当性、計算、状態遷移、分岐網羅 | 層1（型 → Unit → PBT の順に検討） |
| モジュール間・外部システム間の契約 | 層2（Integration） |
| 主要ユーザーフローが端から端まで動くこと | 層2（E2E、厳選） |
| 想定外の操作・組合せでの破綻、UX の違和感 | 層3 |

> **原則**: 「より下の層で検証できるなら、下の層に置く」。上の層にテストを追加する場合は、下層で代替できない理由を PR に明記する。

## 4. 人間とAIの責務分離

| 領域 | 人間 | AI |
|---|---|---|
| 型・ガードレール | **設計する**（ドメイン型、不変条件、禁止事項） | 設計案の提示、型に従った実装 |
| 受入条件 | **合意する**（AC の最終確定） | 起草、抜け漏れ・矛盾の指摘 |
| 仕様変更 | **承認する** | 影響範囲の分析、変更案の PR 提案 |
| テストケース | 重要境界・リスクの指定、レビュー | **大量生成**（因子・水準展開、PBT の Property 候補、境界値） |
| 不具合修正 | 原因分析の妥当性確認、仕様に関わる判断 | **コード即時修復**、層1への還元テスト作成 |
| 探索 | 経験に基づく探索的テスト | **自律探訪**（ブラウザ操作エージェント）、ログ・差分の一次分析 |

**越えてはならない線**

- AI は、テストを通すために**期待値・仕様・文言を書き換えてはならない**。
- AI は、失敗しているテストの**スキップ・削除・アサーション弱体化**を単独で行ってはならない。
- 仕様に影響する変更は常に人間の承認を経る（PR 提案として提示する）。

## 5. 品質ゲート（最低基準）

| ゲート | 条件 | 実行タイミング |
|---|---|---|
| G0 Markdown 検査 | `markdownlint-cli2` の指摘が 0 件、かつ全 Mermaid 図が `mermaid-cli` でレンダリング可能（本ドキュメント群を含む全 `.md`）。ローカルも CI も同一コマンド: `npm ci && npm run lint` | PR／main（CI: `.github/workflows/lint.yml`） |
| G1 静的検査 | 型チェック・Lint がエラー 0 | 保存時／pre-commit |
| G2 層1テスト | Unit・PBT 全件成功 | pre-commit／PR |
| G3 ミューテーション | 変更ファイルの Mutation Score が閾値以上（02b §4） | PR |
| G4 層2テスト | Integration・E2E 全件成功 | PR／マージ前 |
| G5 TRS 整合 | 対応する TRS の AC に紐づくテストが存在し、未解決の Blocking な Open Issue が指す AC が `@pending:<OI-ID>` で明示されている（`@pending` に書けるのは未解決の Blocking な OI-ID だけで、付けられるのはその OI の関連列にある AC だけ） | PR |

G0 の「全 `.md`」は本リポジトリ自身の規則である。導入先では、[05 の適合度診断](./05-adoption-guide.md#3-手順と完了条件)で対象範囲を決める。対象から外す場合は、[05 §4](./05-adoption-guide.md#4-導入モード) の「適用外」の手順（理由と代替の担保の記録）による。

### 5.1 ゲートと必須チェックの対応

`main` は GitHub のルールセット（Protect main）で、PR 必須・force push と削除の禁止・下記の必須チェックを強制する。必須チェックは **`paths:` フィルタを付けず PR で常に実行する**（フィルタがあると、対象外の変更で未実行のまま「待機中」となりマージできなくなるため）。

| ゲート | 必須チェック（ジョブ） | 実装状況 |
|---|---|---|
| G0 | `lint`（`lint.yml`） | 実装済み |
| G1 | `test`（`kotlin-samples.yml`）のコンパイル（`allWarningsAsErrors`）と `./gradlew detekt ktlintCheck` | 実装済み（アーキテクチャ検査は G2 の `test` で実行） |
| G2 | `test`（`./gradlew test`） | 実装済み |
| G3 | `test`（`./gradlew pitest`、PR は差分のみ） | 実装済み。夜間の全体実行は `nightly-mutation.yml`。導入期の例外（[02b §4.1](./02b-execution-and-mutation.md#41-適用タイミングと閾値)）を使う導入先では、補う手段（テストの無い新規・変更クラスを PR で落とす）を導入先で実装する。本リポジトリは例外を使わない |
| G4 | `integration`・`e2e`（`kotlin-samples.yml`、`./gradlew integrationTest` / `./gradlew e2eTest`） | 実装済み。Integration（`@WebMvcTest` + `RestTestClient`、Testcontainers の MySQL を使う DB 統合）は `integration` ジョブ、E2E（Playwright の Chromium、`src/e2eTest`）は `e2e` ジョブで PR に対して実行し、どちらもルールセット（Protect main）の必須チェックに登録している。登録済みの必須チェックは `lint` / `test` / `check` / `integration` / `e2e` で、G4 は層2の失敗でマージを止める。層1の `test` とは別ジョブ（02b §3.2） |
| G5 | `test`（`TraceabilityTest`） | 実装済み。AC に紐づくテストの有無と、未解決の Blocking な Open Issue（TRS の Open Issues 表で区分が `Blocking`、状態が `Open` または `In Discussion`）が指す AC に `@pending:<OI-ID>` があるかと、`@pending` が未解決の Blocking な OI-ID だけを指している（`ISSUE-n`・表に無い ID・Resolved 等の OI-ID は不可）か、`@pending` を付けた AC がその OI の関連列に含まれるかを検査する（[03 §3.4](./03-trs-guideline.md#34-トレーサビリティ)） |

人間のレビューは、一人運用のため承認数を要求せず、`.github/CODEOWNERS` で対象ファイルの責任者を明示するに留める。複数人になった時点で、ルールセットの `require_code_owner_review` を有効にする。

## 6. 用語

| 用語 | 定義 |
|---|---|
| TRS | Test Requirement Specification（テスト要件仕様書）。詳細は 03 |
| PBT | Property-Based Testing。ランダム生成した多数の入力に対し不変条件を検証する手法 |
| AC | Acceptance Criteria（受入条件）。Gherkin 形式で記述 |
| 不具合還元 | 上位層で見つかった不具合を、より速い下位層のテストへ移し替えること（04） |
| AIヒーリング | テスト失敗の原因をAIが分析し、許可された範囲で自動修復すること（04） |

## 7. 改訂

本方針の改訂は PR で行い、人間のレビュー承認を必須とする。AI が単独で本ドキュメントを変更してはならない。

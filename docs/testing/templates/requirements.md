# 要件定義書: <機能名>

> 使い方: このファイルを `<機能ID>-<機能名>.md` としてコピーして使う。置き場所は導入先の要件定義書ディレクトリ（例: `docs/requirements/`）。
> 山括弧 `< >` と `例:` の行は置き換え／削除すること。この要件定義書は、TRS を生成するときの入力になる。書く範囲は [03b §2](../03b-generation-flow.md#2-入力の文書) に従う。
> **節 5 から 7 の要件には ID を付ける。ID は TRS の US/UC の「出典（要件 ID）」に書き、対応を CI が検査する（[03 §3.4](../03-trs-guideline.md#34-トレーサビリティ)）。節 1 から 4 には ID を付けず、要件 ID の形の文字列も書かない。**
> 目次（[03b §2](../03b-generation-flow.md#2-入力の文書)）との一致も、CI が検査する。
> 画面や項目など、実現の方式は[基本設計書](./basic-design.md)に書く。

## 1. 目的と範囲

> 目的は、何のために、誰のために作るかを書く。範囲は、含むことと含まないことを分けて書く。

| 項目 | 内容 |
|---|---|
| 目的 | `<例: 購入者が、誤って注文した商品を発送前に取り消せるようにし、不要な支払いを避けられるようにする>` |
| 範囲に含むこと | `<例: 発送前の注文のキャンセルと、返金処理の開始>` |
| 範囲に含まないこと | `<例: 発送後の返品>` |

### 2.2 用語

> この要件定義書と、対応する基本設計書・TRS で使う用語を、ここに 1 度だけ定義する。ほかの文書は、ここを参照し、用語を書き直さない。
> 使わない言い換えは、同じものを別の語で呼ばないために書く。無ければ「該当なし」とする。書いた語が、この機能の要件定義書・基本設計書・TRS に現れたら、CI が失敗にする（書式は [03a §3](../03a-traceability-checks.md#3-検査が前提とする書式)）。

| 用語 | 意味 | 使わない言い換え |
|---|---|---|
| `<例: キャンセル>` | `<例: 購入者が、発送前の注文を取り消すこと>` | `<例: 取消、解約>` |

## 3. 前提と制約

> 前提は、要件が成り立つために、すでに成り立っているとみなすことを書く。制約は、守らなければならない技術・運用・法令などの条件を書く。

| 区分 | 内容 | 備考 |
|---|---|---|
| 前提 | `<例: 購入者は、ログインした状態で操作する>` | |
| 制約 | `<例: 注文のデータは、国内のデータセンターに置く>` | `<例: 根拠となる規程>` |

## 4. 業務フロー

> 業務が進む順に、誰が何をするかを書く。分岐は「行うこと」に書く。画面の遷移は、基本設計書に書く。

| 順 | 担当 | 行うこと |
|---|---|---|
| 1 | `<例: 購入者>` | `<例: 注文の詳細を開き、キャンセルを申し込む>` |
| 2 | `<例: システム>` | `<例: 発送前なら、注文をキャンセルし、返金処理を始める。発送済みなら、キャンセルを断る>` |

## 5. 機能要件

> システムが提供する機能を、1 行 1 要件で書く。1 つの要件には 1 つのことだけを書く。

| ID | 要件 | 備考 |
|---|---|---|
| REQ-CNL-01 | `<例: 購入者は、発送前の注文をキャンセルできる>` | |
| REQ-CNL-02 | `<例: 注文をキャンセルすると、返金処理が始まる>` | |

|---|---|---|

## 7. 非機能要件

> 性能・安全性などを、TRS の AC で検証できる具体値で書く。「速やかに」「適切に」などの曖昧語を使わない。

| ID | 観点 | 要件 |
|---|---|---|
| REQ-CNL-04 | `<例: 認可>` | `<例: 注文の購入者本人だけが、その注文をキャンセルできる>` |

## 8. 未決事項

> 要件定義を書く中で起きた、まだ決まっていない問いを書く。ID は要件 ID と区別するため `Q-<番号>` とする。行は消さない。担当の列には、決める人を書く。
> 要件 ID の形の文字列は、この表に書かない（[03a §3](../03a-traceability-checks.md#3-検査が前提とする書式)）。
> Q は、どこで決まるかによって次のように書く。
>
> - 要件定義の段階で決まり、要件になる決定: 決まった値は要件の表に書き、要件の表を正とする。Q の行には問いを残し、「決定済み（日付）」を書き足す。値は書かない。
> - 要件定義の段階で決まり、要件にならない決定（「〜しない」など）: 値を Q の行に書く。書式は「決定: `<値>`（YYYY-MM-DD）」とする。
> - 要件定義の段階で決まらなかった Q: [03b の策定フロー](../03b-generation-flow.md#策定フロー)の手順 3 で TRS の Open Issues に起票し、OI-ID を書く（[03 §4](../03-trs-guideline.md#4-open-issues-の履歴化)）。
>
> 起票した Q の決定は、Open Issues を正とする。その決定で範囲が増えるときは、[03 §2.1](../03-trs-guideline.md#21-仕様レイヤー) の 2 に従う。

| ID | 内容 | 担当 | OI-ID |
|---|---|---|---|
| Q-01 | `<例: 発送準備中の注文はキャンセルできるか>` | `<氏名・役割>` | OI-001 |
| Q-02 | `<例: 発送済みの注文はキャンセルできるか。決定済み（YYYY-MM-DD）>` | `<氏名・役割>` | — |
| Q-03 | `<例: キャンセルの理由を記録するか。決定: 記録しない（YYYY-MM-DD）>` | `<氏名・役割>` | — |

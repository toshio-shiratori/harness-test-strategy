### 3. 受入条件（AC）

> 節の区分: 生成物。書き方は 03 §2.1 に従う。
> ルール: 表の 1 行 = 1 AC = 1 つの検証可能な振る舞い／観測可能な結果のみ／曖昧語禁止。期待値の詳細は AC に写さず、根拠の `C-xx`（5.2 の行）で指す。流れの AC も表に 1 行置く。
> テストレベルは `受入` / `結合` / `単体`（01 §2）。検証層は `層1` / `層2（Integration）` / `層2（E2E）`。複数の層で検証するときは、読点で並べる（例: `層1、層2（Integration）`）。E2E は、検証層の列に許可領域を書く。例は `層2（E2E: happy-path）` である（02c §5.1、03 §2.1）。Gherkin では `@e2e:<領域>` を付ける。
> 根拠の列は空にしない。`C-xx`（5.2 の行に結べるとき）、要件 ID、設計 ID（`DES-…`）、OI のどれかを書く。
> Gherkin にするのは、流れの AC と、期待値が未決（`@pending:<OI-ID>`）の AC だけである。未決の AC には期待値を書かない。
> テストはテスト名の先頭に `AC-xx-yy` を置く。括弧やコロンで囲まない（03 §3.4）。テストとの対応は 7 に書く。
> `AC-xx-yy` の `xx`（UC の番号）は、他の TRS と重複させない。既存の TRS が使っていない番号を割り当てる（トレーサビリティ検査が重複を検出する。03 §3.4）。

### 6. Open Issues

> 節の区分: 人が合意する。起票は AI でも人でもよく、解決は人だけが行う。再生成しても行を削除しない。
> **削除禁止。** 解決しても行を残し、状態を `Resolved` にして決定内容・決定者・決定日・反映先を記録する。
> 解決（Resolved）にできるのは人間のみ。決定が覆った場合は旧行を `Superseded` にして新規行を追加する。ただし `Won't Fix` と `Superseded` の行は終端なので、覆すときは行を変えず新規行を追加する（03 §4.2）。
> 区分 `Blocking` が未解決の AC に対するテストは、期待値を確定せず `pending` とする。

|---|---|---|---|---|---|---|---|---|---|---|---|
| OI-001 | `<YYYY-MM-DD>` | `<AI/氏名>` | Blocking | F1-L2, AC-01-05 | 発送準備中の注文はキャンセル可能か | Open | | | | | |
| OI-002 | `<YYYY-MM-DD>` | `<AI/氏名>` | Non-blocking | AC-01-01 | キャンセル完了通知の文言 | Open | | | | | |
| OI-003 | `<YYYY-MM-DD>` | `<AI/氏名>` | Blocking | F1-L5, AC-01-06 | キャンセル済みの注文への再キャンセルは成功扱いかエラーか | Open | | | | | |

**状態の凡例**: `Open` / `In Discussion` / `Resolved` / `Superseded` / `Won't Fix`。`Superseded` は置換先 ID を記載し、`Won't Fix` は理由を必須とする。遷移は 03 §4.2

**機械検査のルール**（失敗条件の全体は 03 §3.4）

- 区分は `Blocking` / `Non-blocking`、状態は上の5値のどれかにする（装飾や表記ゆれは検査が失敗する）。
- 未解決（`Open` / `In Discussion`）の `Blocking` は、関連列に指す AC を書く。書き方は `AC-01-05` または範囲 `AC-01-05〜06`。その AC の Gherkin のタグ行に `@pending:<OI-ID>` を付ける。
- `@pending:<OI-ID>` に書けるのは、この表の未解決の `Blocking` な OI-ID だけである。付けられるのは、その OI の関連列にある AC だけである。実装待ちは Issue / PR で管理し、`@pending:ISSUE-n` は使わない。

## レビューチェックリスト

- [ ] 仕様レイヤーとテスト設計レイヤーが分離されている
- [ ] 生成物の節が、手で編集されていない（直しは入力の文書か、人が合意する節にある）
- [ ] 生成物の、既存の ID に結び付く記述の変化（消える、中身が変わる、AC が `@pending` になる）を、人が確かめた（03 §5.1）
- [ ] US/UC の出典が実在する要件 ID で、要件定義書の全要件 ID がどれかの出典に現れる
- [ ] 全 AC が表の 1 行で、テストレベル・検証層・根拠（`C-xx`、要件 ID、設計 ID、OI のどれか）が書かれている。Gherkin は流れの AC と `@pending` の AC だけである
- [ ] 5.2 の根拠が、実在する要件 ID、設計 ID、OI を指している
- [ ] AC と US/UC が、要件定義書の目的、前提と制約、業務フロー（節 1〜4）と矛盾しない
- [ ] 期待値の根拠が仕様／デザインであり、既存コード由来ではない
- [ ] 因子の無効水準と、型で排除できる制約が明記されている
- [ ] 因子制約に、禁止組合せと組合せ別の期待結果がある
- [ ] Blocking の Open Issue が未解決のまま実装に進んでいない
- [ ] Open Issues の履歴（解決済みを含む）が残っている
- [ ] `@pending` の AC を除く全 AC にテストが紐づいている

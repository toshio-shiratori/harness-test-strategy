# 05 導入手順書: パイロットの記録

この文書は、[05 既存プロジェクトへの導入手順書](../testing/05-adoption-guide.md)を作る過程で行ったパイロット（最初の適用対象での試行）の記録である。標準の要求ではなく、配布もしない。05 の規範は、この記録を読まなくても成り立つ。

- 適用対象は非公開のプロジェクトである。非公開側の Issue 番号・リンク・内部構成・正確な実測値は載せない（数値は桁感の概数）。
- 05 の規範は、机上で書いた骨子に、このパイロットの結果を反映して整えた。反映した箇所と骨子を直した箇所の対応は [§7](#7-更新履歴) にある。
- 「出典」は、パイロット対象の非公開プロジェクトでの記録を指す（旧 05 は出典の中身を明示していないため、パイロットの取り込み経緯からの推定である）。その記録は公開しないため、ここでは確認できなかった事項を [§8](#8-出典では確認できなかった事項) にまとめて残す。

## 1. パイロットの前提

- ラチェット文化のある既存プロジェクトだった。導入前から、ビルドに Lint と層別のカバレッジ閾値があり、設計書のバイト数や層の境界を検査する自前のラチェットが十数本あった。
- ブランチ保護が使えないプランだったため、強制力はプッシュ前フック・ラチェット・PR テンプレートで担保した（05 §3 ④）。
- 範囲は、診断、TRS のパイロット、PBT、ミューテーションテスト、型ガードレールである。

## 2. 手順ごとの実例

05 §3 の各手順に対応する実例である。

### ① 適合度診断（05 §3 ①）

標準への準拠宣言を1行足しただけで、設計書のバイト数の上限を検査する既存ラチェットが赤くなることが、診断で分かった。記入例は [§4](#4-適合度診断の記入例) にある。

### ② 導入モードの選択（05 §3 ②）

- 判断事項（新しい依存の追加の可否、検査ツールの採否、TRS の置き場所、ミューテーションテストの実行頻度）は、診断の直後に確認し、作業を Issue に起票する前に決めた。
- 新しい依存（ミューテーションテストのツール）はスパイクを挟んだ。本導入に進む基準を先に置いた実例と、実測が基準を超えた実例が [§3](#3-導入モードの選択) にある。

### ④ ラチェット化（05 §3 ④）

ブランチ保護が使えないプランで、次の3つで担保した。05 §3 ④ の表は、この3つを一般化した例である。

| 担保手段 | 何を強制するか（本書の補足） | 限界（本書の補足） |
|---|---|---|
| プッシュ前フック | ローカルで悪化を検出し、プッシュを止める | 設定は利用者の環境ごとに要り、迂回できる |
| ラチェット | 固定値からの悪化を、テストの失敗として検出する | 必須チェックが無い環境では、CI が赤でもマージを止められない |
| PR テンプレート（不具合還元の DoD） | 不具合還元の完了条件の欄を、PR の作成時に示す | 欄を埋めたかどうかは、人間が確認する |

### ⑤ パイロット領域での検証（05 §3 ⑤）

領域の選び方: 権限と状態遷移がコメントで明示された集約を1つ選んだ。業務ルールが設計書の番号で参照でき、既存のテストもあるため、AC の出典を決めやすかった。

検証で分かった摩擦:

1. **テスト基盤の版の食い違い。** 依存管理の下で、テスト実行基盤の launcher だけが古い版に固定され、ミューテーションツールの子プロセスが落ちた。`force` では直らず、依存の解決戦略で engine の版に揃えた。この変更は他のテストタスクの classpath にも効く。
2. **ローカルで回したタスクと、CI が回すタスクの差。** 上の版揃えを、単体・統合テストの classpath にだけ入れ、E2E の classpath に入れ忘れた。ローカルは `clean build` だけで、CI が別に回す E2E を含めていなかったため、CI で初めて落ちた。この教訓は、05 §3 ③⑤ の完了条件にした。
3. **ミューテーションツールの設定。** テスト対象クラスの指定と、テストのタグを子プロセスに渡す設定が要る。未指定だと、本体クラスをテストとして実行したり、統合テストまで拾ったりする。
4. **紐づけ検査の自己参照。** 紐づけ検査のラチェットが、文書に書いた例示を自分で拾って赤くなる。文書に例を書くときの外し方を、エラーメッセージとドキュメントに書いた。

### ⑥ 水平展開（05 §3 ⑥）

型ガードレールの水平展開の実例である。

1. **単位と順序。** 方針（ADR）、パイロット集約、残りの集約の順に、1段を1つの PR として進めた。差分の大きい集約は、着手前に ADR で範囲と据置を決めた。
2. **変換位置の先行固定。** 型を境界の外に出さない変換位置を、先に永続化と表示の2か所の境界に固定した。外部契約（API・DB スキーマ・JSON）は変わらなかった。
3. **コンパイルが通るのに壊れる箇所。** 次の3つがあった。後ろの2つは、型検査では見つからないので、全数確認が要る。
   - 文字列補間: 型の `toString` が出る。
   - テストの等価比較: 型を取り違えても、実行時にしか外れない。
   - ログ引数: `Any?` なので、型が漏れてもコンパイルが通り、テストにも出ない。
4. **据置。** 運用していない機能や、表示用の派生値は据置にした。据置は ADR に書き、Issue のチェックリストにも「見送り」の行を残した。
5. **チケットの切り方。** 子チケットの数は「守る性質の数」で決め、PR の数は「段」として自由に増やした。段はチェックリストで管理し、段ごとに新しい Issue は立てない。分割は1回だけ使った。
6. **AI への委譲。** 指示書に、範囲外を書き換えないことを明記する必要があった。永続化層の値（素の整数）をドメインの型と取り違えて書き換えた例があり、統合テストが1件落ちて検出した。

## 3. 導入モードの選択

05 §4 に対応する実例である。

- 「導入時に赤くしない」は最初から選んだ。標準の閾値（ミューテーション 80% など）を最初から課す案は、導入時に赤くなり既存の運用を止めるため、起票の時点で却下した。
- 途中で変えたのは、ミューテーションの**評価軸**である。

| | 当初の案 | 見直し後 |
|---|---|---|
| PR | 全体を回し、Mutation Score の悪化を禁止する | 差分実行で、テストの強度（カバー済みのミュータントのうち殺せた割合）だけを評価する |
| 週次 | （当初の案には無い） | 全体実行で、Mutation Score を評価する |

- 変えた決め手は2つある。CI の runner での全体実行が、事前に置いた基準（数分以内）を超えた。さらに差分実行では、テストの無いクラスのミュータントが Mutation Score に混ざり、触ったクラスの評価として不適切だった。
- 限界: テストの無い新規クラスは、差分では通る。その検出は、週次の全体実行に任せた。
- 迷った点: 「実行頻度」と「評価軸」は別の判断だった。頻度を落とす前に、評価軸が目的に合っているかを確認した方がよい、というのがパイロットの所感である。
- 標準の閾値（80% / 70%）は変えていない。この見直しは [02b §4.1](../testing/02b-execution-and-mutation.md) の「導入期の例外（評価軸）」の対象だが、実例は例外の条件1（補う手段）を満たしていなかった（上の「限界」がその状態である）。条件2・3を満たしたかは、出典では確認できない（[§8](#8-出典では確認できなかった事項)）。例外の条件は 02b §4.1 を参照する。

その他の実例:

- G0（文書検査）: 診断で G0 を対象にしなかった（[§4](#4-適合度診断の記入例)）。理由と代替の担保を記録していたかは、出典では確認できない。
- 据置: 運用していない機能や表示用の派生値を据置にした。
- 運用フェーズの不起票: 破られた実績も機械検証の手段も無い間は、運用の仕組み化を起票しなかった。据置の記録を残したかは、出典では確認できない。

## 4. 適合度診断の記入例

旧 05 §5 の記入例（パイロット）である。非公開のバックエンド（Kotlin / Spring Boot、テストは Kotest と MockK、統合テストは Testcontainers）に適用した診断の要約である。この診断では、文書検査（G0）を対象にしなかった。要約のため、表はテンプレートの列ではなく診断と取り込み方針の2列にし、導入モード名は省略した。

| 要素 | 診断 | 取り込み方針 |
|---|---|---|
| G1 静的検査 | 充足。ただし網羅 `when` の検査は無効で、`else ->` が十数件ある | 件数をベースラインに固定し、悪化のみ禁止 |
| G2 層1テスト | 単体・統合・層別カバレッジは充足。PBT は無い | プロパティテストの依存を追加 |
| G3 ミューテーション | 無い | ドメイン層だけに限定して導入。まずスパイク |
| G4 層2テスト | 充足（標準より先行） | 変更なし |
| G5 TRS 整合 | 無い | 1集約でパイロットし、紐づけ検査を足す |
| 型ガードレール | 検証付きの型が1つだけ。ドメインの値は素の整数 | 集約単位で段階導入 |
| アーキテクチャ検査 | 自前のトークン走査ラチェットが同等の機能を持つ | 既存を拡張。新しいツールは入れない |
| テスト保護・不具合還元 | 規則も検査も無い。テストの無効化は 0 件 | ラチェットで 0 を固定し、PR テンプレートに完了条件を置く |

## 5. ベースライン固定の実例

05 §6 に対応する、固定先と固定値の選び方である。

1. **固定先は、1つの値につき1か所にした。** ミューテーションの閾値はビルド設定の1か所、違反件数と設計書のバイト数はラチェットのテストの定数に置いた。設計書に数値を書く案は、設計書が上限ちょうどで二重管理になるため却下した。方針（ADR）には数値を置かない。
2. **件数の基準値は、スラックなしにして、増えても減っても赤にした。** 減っても赤くなるので、改善した PR は基準値の更新を伴う（[§6](#6-閾値の引き上げを提案する契機)）。
3. **全体の Mutation Score は、テストの有無に支配された。** テストの無いクラスのミュータントが分母に入り、全体は低く出る。実測は七割前後で、カバー済みのコードだけなら九割台だった。標準の 80% を最初から課すと、テストの空白地帯が閾値違反として現れる。
4. **整数の閾値は、実測値を切り捨てた値にした。** 実測が小数のとき、四捨五入した値を閾値にすると、初日から赤くなりうる。さらに1ポイントの余裕を置くと、タイムアウトの判定が1〜2件ぶれても赤にならない。

## 6. 閾値の引き上げを提案する契機

05 §7 に対応する実例である。発生したものと、していないものを区別して書く。

| 項目 | 状況 | 内容 |
|---|---|---|
| 件数が減ったとき | 実例あり | 設計の改善で `else ->` の件数が実際に減ると、「減っても赤」のラチェット（[§5](#5-ベースライン固定の実例)）が止めた。改善した PR が、同じ PR で基準値を下げた。そのための承認の手続きは追加していない |
| ミューテーションの閾値の引き上げ | 未発生 | 見込む契機は、テストを足した PR が Mutation Score を押し上げたとき。上げるのはその PR 自身で、同じ PR で閾値を更新する |
| 週次の全体実行の結果 | 懸念であり、実例なし | 引き上げの契機として使える。ただし、週次の結果が誰にも見られなくなると、ベースラインが形骸化する |

### 標準側の扱い

パイロットの実例のうち、次の3点を標準に反映した（Issue #71 の判断）。

- G3 の評価軸: 導入期の例外として条件付きで認める（02b §4.1 の注記、01 §5.1。実例は [§3](#3-導入モードの選択)）。閾値（80% / 70%）は変えていない。
- 運用フェーズの不起票: 破られた実績も機械検証の手段も無い間に限り、据置の記録と同じ形式の記録を条件に許容する。AI ヒーリングを行う場合の 04 §3.1〜§3.5 は免除しない（04 §3・04 §5。実例は [§3](#3-導入モードの選択)）。
- G0 の適用外: 01 §5 の「全 `.md`」は本リポジトリ自身の規則とし、導入先では診断で対象範囲を決める。外す場合は 05 §4 の「適用外」の手順による（実例は [§3](#3-導入モードの選択)・[§4](#4-適合度診断の記入例)）。

週次結果の担当は、標準で求めることを見送った。実例の無い懸念であり、05 §3 ⑦ は承認者を決める条件を既に持つためである。再評価の条件は、2 件目のパイロットの結果が出た時、または週次結果の形骸化の実例が出た時とする。

## 8. 出典では確認できなかった事項

旧 05 の本文に「出典では確認できない」と書いていた事項である。出典（パイロット対象の非公開プロジェクトでの記録）では、次の点を確認できなかった。05 の規範はこれらに依存しない。

| 事項 | 関連する規範 |
|---|---|
| G0 を対象にしなかったとき、理由と代替の担保を記録していたか | 05 §4 の「適用外」の手順 |
| 運用フェーズの不起票で、据置の記録を残したか | 05 §4 の運用フェーズの不起票 |
| 評価軸の見直しが、02b §4.1 の導入期の例外の条件2（記録）・条件3（復帰の再評価）を満たしたか | 02b §4.1 の導入期の例外 |
